1. El paradigma orientado a objetos

La programación orientada a objetos (POO) modela un sistema como un conjunto de objetos que colaboran intercambiando mensajes. Cada objeto une estado (datos) y comportamiento (operaciones) en una sola unidad. Frente al paradigma estructurado (datos y funciones separados, descomposición funcional top-down), la POO descompone el problema en entidades del dominio.

1.2. Los cuatro pilares de la POO

1.3. Conceptos asociados

  • Mensaje: petición que un objeto envía a otro para que ejecute un método (receptor.metodo(args)).

  • Identidad: cada objeto es distinguible aunque tenga el mismo estado que otro (en Java, == compara identidad y equals() igualdad de estado).

  • Ligadura dinámica (late binding): el método a ejecutar se decide en tiempo de ejecución según el tipo real del objeto. La ligadura estática se decide en compilación (sobrecarga, métodos static, final, private).

  • Persistencia: capacidad de un objeto de sobrevivir al proceso que lo creó (serialización, ORM).

1.5. Análisis y diseño orientado a objetos (A/DOO)

  • Análisis OO (AOO): identifica clases y objetos del dominio del problema (el qué). Herramientas: casos de uso, modelo de dominio.

  • Diseño OO (DOO): define la solución software (el cómo): clases de diseño, responsabilidades, colaboraciones, patrones.

  • Programación OO (POO): implementa el diseño en un lenguaje OO.

  • Métodos clásicos previos a UML: Booch, OMT (Rumbaugh: modelos de objetos, dinámico y funcional), OOSE/Objectory (Jacobson: casos de uso), Coad-Yourdon, Shlaer-Mellor. Su unificación dio lugar a UML y al Proceso Unificado (RUP), iterativo e incremental, dirigido por casos de uso y centrado en la arquitectura, con fases Inicio, Elaboración, Construcción y Transición.

  • Tarjetas CRC (Clase-Responsabilidad-Colaborador; Beck y Cunningham): técnica ligera para descubrir clases.

  • GRASP (Craig Larman): patrones de asignación de responsabilidades: Experto en información, Creador, Controlador, Bajo acoplamiento, Alta cohesión, Polimorfismo, Fabricación pura, Indirección, Variaciones protegidas.

2. Elementos y componentes software: objetos, clases y métodos

Una clase es la plantilla o molde que define atributos y métodos; un objeto es una instancia concreta de una clase, creada en tiempo de ejecución (en Java y C#, con new, en el heap).

2.1. Objeto

Un objeto tiene tres propiedades (Booch):

  • Estado: valores de sus atributos en un instante.

  • Comportamiento: lo que sabe hacer (sus métodos); cambia su estado o envía mensajes.

  • Identidad: lo distingue de cualquier otro objeto, aunque tengan el mismo estado.

2.4. Ejemplo

public class Expediente {
    private static int contador = 0;   // atributo de clase
    private final String id;           // atributo de instancia
    private Estado estado;

    public Expediente(String id) {     // constructor
        this.id = id;
        this.estado = Estado.ABIERTO;
        contador++;
    }
    public String getId() { return id; }          // getter
    public void cerrar() { estado = Estado.CERRADO; }
    public static int total() { return contador; } // método de clase
}

Expediente e = new Expediente("2026/001"); // instanciación

2.5. Otros elementos

  • Clase abstracta: no se puede instanciar; puede tener métodos abstractos (sin cuerpo) y concretos.

  • Interfaz: contrato de métodos que una clase implementa (implements). Desde Java 8 admite métodos default y static; desde Java 9, private.

  • Clase final / sellada: no se puede heredar (final en Java, sealed en C#). Java 17 añadió clases sealed con permits (herencia restringida a una lista).

  • Clase interna / anidada y clase anónima; lambdas (Java 8) para interfaces funcionales.

  • Enumeraciones (enum) y records (Java 16, C# 9): clases inmutables de datos con equals, hashCode y toString generados.

  • Genéricos (plantillas en C++): clases parametrizadas por tipo, List<T>; dan polimorfismo paramétrico.

  • Paquete / espacio de nombres (package, namespace) y módulo (JPMS, Java 9): agrupan clases.

  • Componente: unidad de software reemplazable con interfaces bien definidas (JavaBeans, EJB, ensamblados .NET). Un JavaBean tiene constructor sin argumentos, propiedades con get/set y es serializable.

  • Recolector de basura (garbage collector): libera automáticamente los objetos no referenciados (Java, C#); C++ no lo tiene de serie (gestión manual, delete, smart pointers).

3. Herencia, polimorfismo, sobrecarga y sobrescritura

La herencia permite que una subclase reciba atributos y métodos de su superclase y los amplíe o redefina; el polimorfismo permite tratar objetos de distintas subclases a través de la misma referencia de la superclase.

3.1. Herencia

  • Terminología: superclase / clase base / clase padre y subclase / clase derivada / clase hija. Relación “es-un” (is-a), frente a la composición, que es “tiene-un” (has-a).

  • Generalización (de abajo arriba: sacar lo común a una superclase) y especialización (de arriba abajo: crear subclases).

  • Herencia simple: una sola superclase directa (Java, C# para clases). Herencia múltiple: varias superclases (C++, Python, Eiffel). Java y C# la simulan con varias interfaces.

  • Problema del diamante: con herencia múltiple, D hereda de B y C, que heredan de A; ¿qué versión de un método de A hereda D? C++ lo resuelve con herencia virtual; Python con el MRO (linealización C3).

  • En Java toda clase hereda implícitamente de java.lang.Object; en C#, de System.Object.

  • Los constructores no se heredan; el de la subclase llama al de la superclase (super(...)), explícita o implícitamente.

  • Principio “composición mejor que herencia” (GoF): favorecer la composición de objetos frente a la herencia de clases para reducir acoplamiento.

  • Principio de sustitución de Liskov: donde se espera un objeto de la superclase debe poder usarse cualquier subclase sin alterar el correcto funcionamiento.

class Calculadora {
    int sumar(int a, int b) { return a + b; }            // sobrecarga
    double sumar(double a, double b) { return a + b; }   // sobrecarga
}
class Figura { double area() { return 0; } }
class Circulo extends Figura {
    private double r;
    @Override double area() { return Math.PI * r * r; } // sobrescritura
}

  • Métodos static no se sobrescriben: se ocultan (hiding). Métodos final (Java) o sealed override (C#) no pueden redefinirse. Métodos private no se heredan, por lo que tampoco se sobrescriben.

  • En C# los métodos no son virtuales por defecto: hay que marcar virtual en la base y override en la derivada; new oculta. En Java todo método de instancia no final, no private y no static es virtual.

  • Sobrecarga de operadores: C++, C#, Python, Kotlin la permiten; Java no (salvo + para String, predefinido).

4. Principios de diseño orientado a objetos

Un buen diseño OO busca alta cohesión y bajo acoplamiento; los principios SOLID (Robert C. Martin, acrónimo de Michael Feathers) concretan cómo conseguirlo.

4.1. Cohesión y acoplamiento

  • Cohesión: grado en que los elementos de un módulo están relacionados con una única tarea. Se busca alta. Escala de peor a mejor: coincidental, lógica, temporal, procedimental, comunicacional, secuencial, funcional (la mejor).

  • Acoplamiento: grado de dependencia entre módulos. Se busca bajo. Escala de peor a mejor: de contenido, común, externo, de control, de estampado (stamp), de datos (el mejor).

  • Ley de Demeter (“principio del mínimo conocimiento”): un objeto solo habla con sus “amigos” inmediatos; evitar a.getB().getC().hacer().

  • DRY (Don't Repeat Yourself), KISS (Keep It Simple), YAGNI (You Aren't Gonna Need It).

  • Diseño por contrato (Meyer): precondiciones, postcondiciones e invariantes de clase.

4.2. SOLID

LetraPrincipioIdea en una líneaSe viola cuando…
SResponsabilidad única (SRP)Una clase debe tener un solo motivo para cambiarFactura calcula, imprime y guarda en BD
OAbierto/cerrado (OCP, Meyer)Abierta a la extensión, cerrada a la modificaciónAñadir un tipo obliga a tocar un switch

  • Inversión de control (IoC): el framework llama a tu código (principio de Hollywood: “no nos llames, ya te llamaremos”).

  • Inyección de dependencias (DI): forma de IoC en la que un contenedor suministra las dependencias (por constructor, setter o atributo). Ejemplos: CDI (Jakarta EE), Spring, el contenedor de ASP.NET Core. No confundir DIP (principio) con DI (técnica).

// DIP + DI por constructor
public interface Repositorio { void guardar(Expediente e); }

public class ServicioExpedientes {
    private final Repositorio repo;               // depende de la abstracción
    public ServicioExpedientes(Repositorio repo) { this.repo = repo; }
}

5. Lenguajes orientados a objetos

Los lenguajes OO se clasifican en puros (todo es un objeto: Smalltalk, Ruby, Eiffel) e híbridos (combinan OO con tipos primitivos o con el paradigma estructurado: C++, Java, C#, Python, PHP, Object Pascal).

5.1. Clasificaciones

  • Basados en clases (Java, C#, C++, Python) frente a basados en prototipos (los objetos se clonan de otros objetos: JavaScript, Self, Lua). JavaScript añadió sintaxis class en ES2015/ES6, pero sigue siendo prototipado por debajo.

  • Tipado estático (comprobación en compilación: Java, C#, C++, Kotlin, Swift) frente a dinámico (en ejecución: Python, Ruby, Smalltalk, JavaScript, PHP). Duck typing: “si camina como un pato…”, importa el comportamiento, no el tipo declarado.

  • Compilados a código nativo (C++, Swift, Objective-C), a código intermedio para máquina virtual (Java → bytecode para la JVM; C# → CIL para el CLR; Kotlin y Scala → JVM) o interpretados (Python, Ruby, PHP, aunque usan bytecode interno).

6. Patrones de diseño

Un patrón de diseño es una solución probada y reutilizable a un problema recurrente de diseño en un contexto dado. La referencia es Design Patterns: Elements of Reusable Object-Oriented Software (1994), de la Banda de los Cuatro (GoF): 23 patrones en 3 categorías (5 creacionales, 7 estructurales y 11 de comportamiento). La idea procede del arquitecto Christopher Alexander (A Pattern Language, 1977).

  • Elementos de un patrón (GoF): nombre, problema, solución y consecuencias.

  • Niveles: patrones de arquitectura (MVC, capas, microservicios), patrones de diseño (GoF) e idiomas (propios de un lenguaje).

  • Antipatrón: solución habitual pero contraproducente (God object o clase Dios, código espagueti, golden hammer, lava flow).

  • Por ámbito, GoF distingue patrones de clase (relaciones por herencia, estáticas: Factory Method, Adapter de clase, Interpreter, Template Method) y de objeto (composición, dinámicas: el resto).

6.1. Creacionales (5): cómo se crean los objetos

Para recordar el reparto: 5 + 7 + 11 = 23 (creacionales, estructurales, de comportamiento). Los creacionales responden a quién crea, los estructurales a cómo se ensambla y los de comportamiento a quién hace qué y cómo se comunican.

Pares que se confunden en test:

  • Adapter cambia la interfaz; Decorator la mantiene y añade funciones; Proxy la mantiene y controla el acceso; Facade simplifica un subsistema entero.

  • Strategy lo elige el cliente; State cambia solo según el estado interno.

  • Factory Method usa herencia (un método); Abstract Factory usa composición (un objeto que crea familias).

7. Lenguaje de modelado unificado (UML)

UML es un lenguaje gráfico para especificar, visualizar, construir y documentar sistemas software. No es una metodología ni un proceso: es una notación, independiente del lenguaje de programación y del proceso. Lo mantiene el OMG (Object Management Group); la versión vigente es UML 2.5.1 (diciembre de 2017) (la anterior, UML 2.4.1, se publicó como norma ISO/IEC 19505). Fuente: OMG, About UML.

7.1. Historia y fundamentos

  • Nace de unificar los métodos de Booch, Rumbaugh (OMT) y Jacobson (OOSE) en Rational Software. UML 1.1 adoptado por el OMG en 1997; UML 2.0 en 2005 (de 9 a 13 diagramas); UML 2.2 añadió el diagrama de perfiles (14); 2.5 (2015) simplificó la especificación; 2.5.1 (2017) es la última.

  • Arquitectura de cuatro capas del OMG (MOF): M3 metametamodelo (MOF), M2 metamodelo (UML), M1 modelo del usuario, M0 objetos en ejecución.

  • Mecanismos de extensión: estereotipos («entity», «interface»), valores etiquetados (tagged values) y restricciones (entre llaves {ordered}), agrupados en perfiles.

  • OCL (Object Constraint Language): lenguaje formal para restricciones, invariantes, pre y postcondiciones.

  • XMI: formato XML para intercambiar modelos entre herramientas. MDA (Model Driven Architecture): PIM (modelo independiente de la plataforma) → PSM (específico) → código.

  • 4+1 vistas de Kruchten: lógica, de procesos, de desarrollo (implementación), física (despliegue) + escenarios (casos de uso).

7.2. Los 14 diagramas de UML 2.5

UML 2.5 tiene 14 diagramas: 7 de estructura (estáticos) y 7 de comportamiento (dinámicos), de los cuales 4 son de interacción.

  • Orden de fuerza del acoplamiento: dependencia < asociación < agregación < composición < generalización.

  • Clase asociación: clase unida a una asociación por línea discontinua (ej.: Matrícula entre Alumno y Asignatura). Asociación reflexiva: de una clase consigo misma. Asociación cualificada: con un calificador que reduce la multiplicidad.

  • Interfaz: rectángulo con «interface», o notación de piruleta (interfaz provista, círculo) y enchufe/semicírculo (interfaz requerida).

El actor (muñeco) es un rol externo al sistema: persona, otro sistema o dispositivo. El límite del sistema se dibuja como un rectángulo.

Esquema de repaso

  • POO: objetos que unen estado + comportamiento + identidad y colaboran por mensajes. Pilares: abstracción, encapsulamiento, herencia y polimorfismo.

  • Primer lenguaje OO: Simula 67; POO pura y origen de MVC: Smalltalk.

  • Clase = plantilla; objeto = instancia; constructor = mismo nombre, sin retorno, no se hereda.

  • Visibilidad UML: + público, − privado, # protegido, ~ paquete. En Java protected incluye el paquete.

  • Herencia simple en Java y C# (múltiple solo de interfaces); múltiple en C++ y Python (problema del diamante).

  • Clase abstracta: puede tener estado y constructores; interfaz: contrato, varias por clase.

  • Sobrecarga: misma clase, distinta lista de parámetros, compilación. Sobrescritura: subclase, misma firma, ejecución (@Override).

  • El tipo de retorno no basta para sobrecargar; los constructores se sobrecargan pero no se sobrescriben.

  • Polimorfismo: inclusión, paramétrico (genéricos), ad hoc (sobrecarga, coerción).

  • Objetivo de diseño: alta cohesión, bajo acoplamiento; mejor cohesión funcional, mejor acoplamiento de datos.

  • SOLID: responsabilidad única, abierto/cerrado, Liskov, segregación de interfaces, inversión de dependencias. DIP es un principio; DI es la técnica (CDI, Spring, ASP.NET Core).

  • Ventajas OO: reutilización, mantenibilidad, extensibilidad. Inconvenientes: aprendizaje, rendimiento, sobrediseño, desajuste objeto-relacional.

  • GoF 1994: 23 patrones = 5 creacionales + 7 estructurales + 11 de comportamiento.

  • Creacionales: Abstract Factory, Builder, Factory Method, Prototype, Singleton.

  • Estructurales: Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy.

  • Comportamiento: Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor.

  • MVC: modelo (datos y negocio), vista (presentación), controlador (entrada y coordinación).

  • UML: notación del OMG, versión 2.5.1 (2017), no es metodología; 14 diagramas = 7 estructura + 7 comportamiento (4 de interacción).

  • Relaciones: dependencia (discontinua + flecha), asociación (continua), agregación (rombo vacío), composición (rombo relleno), generalización (continua + triángulo vacío), realización (discontinua + triángulo vacío).

  • Casos de uso: «include» obligatorio (flecha al incluido), «extend» opcional (flecha al base).
