1. Repositorios: estructura y actualización

Un repositorio es un almacén centralizado y controlado de elementos del desarrollo (código, modelos, documentos, binarios) con sus metadatos y su historial, que permite compartirlos, versionarlos y reutilizarlos.

1.1 Tipos de repositorio

TipoContenidoEjemplos
De código fuente (control de versiones)Ficheros fuente y su historialGit, Subversion (SVN), Mercurial
De artefactos / binariosLibrerías compiladas, paquetes, imágenesMaven Central, npm, PyPI, NuGet, Nexus, JFrog Artifactory, Docker Hub
De paquetes del sistemaSoftware para instalar en el SOAPT (Debian/Ubuntu), DNF/YUM (Red Hat)
CASE / de modelosModelos, diagramas, especificaciones y sus relacionesRepositorio de una herramienta CASE (diccionario de datos)
De activos reutilizablesComponentes y soluciones compartidasCentro de Transferencia de Tecnología (CTT) del PAe; code.europa.eu (UE)
DocumentalDocumentos con metadatos y flujosGestores documentales, wikis

1.2 Repositorio CASE

En las herramientas CASE (Computer Aided Software Engineering), el repositorio (o diccionario) es el núcleo: guarda la información de todas las fases (requisitos, modelos de datos y procesos, diseño, código) de forma integrada y permite comprobar consistencia, trazabilidad y generar documentación o código.

Funciones del repositorio: almacenamiento de objetos y relaciones, control de integridad y consistencia, control de versiones y configuraciones, control de acceso y concurrencia, importación/exportación e informes.

1.3 Estructura de un repositorio de código

Subversion (SVN) — convención de directorios:

/proyecto
  /trunk      línea principal de desarrollo
  /branches   ramas (copias baratas de trunk)
  /tags       instantáneas fijas (versiones publicadas)

Git — estructura interna:

ZonaQué es
Directorio de trabajoFicheros que se editan
Área de preparación (staging, índice)Cambios seleccionados para el próximo commit (git add)
Repositorio local (.git)Historial completo de commits
Repositorio remoto (origin)Copia en un servidor (GitHub, GitLab)

Objetos de Git: blob (contenido de un fichero), tree (directorio), commit (instantánea con autor, fecha, mensaje y padre/s), tag anotada. Cada objeto se identifica por su hash (SHA-1 por defecto; SHA-256 disponible).

Ficheros habituales en la raíz: README.md, LICENSE, .gitignore (ficheros que no se versionan), CHANGELOG.md, CONTRIBUTING.md, y el descriptor de construcción (pom.xml en Maven, build.gradle en Gradle, package.json en npm).

1.4 Repositorios de artefactos y dependencias

  • Maven identifica cada artefacto por sus coordenadas groupId:artifactId:version; busca primero en el repositorio local (~/.m2) y después en los remotos (Maven Central o un repositorio corporativo).

  • Versiones SNAPSHOT (en desarrollo, cambian) frente a release (inmutables).

  • Versionado semántico (SemVer) MAYOR.MENOR.PARCHE: MAYOR = cambios incompatibles; MENOR = funciones compatibles; PARCHE = correcciones compatibles.

  • Ficheros de bloqueo (package-lock.json) fijan las versiones exactas.

1.5 Actualización del repositorio

  • Control de acceso por roles (lectura, escritura, administración); ramas protegidas.

  • Operaciones de actualización: en SVN svn update (traer) y svn commit (enviar); en Git git fetch/git pull (traer) y git push (enviar).

  • Concurrencia: modelo bloquear-modificar-desbloquear (lock, pesimista) frente a copiar-modificar-fusionar (optimista, el de Git y por defecto en SVN).

  • Gestión de la configuración: identificar los elementos de configuración, controlar los cambios, registrar su estado y auditar. Una línea base (baseline) es una configuración revisada y aprobada que solo cambia mediante el procedimiento formal de control de cambios.

  • Copias de seguridad, réplicas (mirrors) y políticas de retención.

2.5 Documentación de API: OpenAPI y Swagger

  • OpenAPI Specification (OAS): estándar para describir API REST en YAML o JSON (rutas, operaciones, parámetros, esquemas, respuestas, seguridad). La mantiene la OpenAPI Initiative (Linux Foundation); nació como especificación Swagger y se renombró en 2016 (desde la versión 3.0).

  • Swagger es hoy el nombre de las herramientas (SmartBear): Swagger UI (documentación interactiva para probar la API), Swagger Editor, Swagger Codegen.

  • Enfoques: design-first / contract-first (primero el contrato y luego el código) o code-first (anotaciones en el código que generan el contrato, p. ej. springdoc).

  • Otros formatos: WSDL (servicios SOAP), AsyncAPI (API basadas en eventos y mensajería), RAML, API Blueprint; esquemas GraphQL.

3. Metodologías de desarrollo: ciclos de vida y Métrica v3

Un ciclo de vida define las fases del software y su orden; una metodología añade qué actividades, técnicas, productos y roles hay en cada fase. Norma de referencia de procesos: ISO/IEC/IEEE 12207.

3.1 Modelos de ciclo de vida

ModeloIdeaVentajasInconvenientes
Cascada (Royce, 1970)Fases secuenciales: requisitos → análisis → diseño → codificación → pruebas → mantenimiento; cada una termina antes de la siguienteSencillo, fácil de planificar y documentarRígido; el cliente no ve nada hasta el final; errores de requisitos caros
Modelo en VCascada que asocia cada fase de definición con su nivel de pruebaPlanifica la verificación desde el inicioIgual de rígido
PrototipadoVersión preliminar para validar requisitos con el usuario; puede ser desechable o evolutivoAclara requisitos dudososRiesgo de convertir el prototipo en producto
IncrementalEntregas sucesivas, cada una añade funcionalidad (cascadas solapadas)Valor temprano, menos riesgoRequiere buena arquitectura inicial
IterativoSe repite el ciclo refinando el productoRetroalimentación continuaDifícil fijar alcance y coste
Espiral (Boehm, 1986)Iteraciones con análisis de riesgos explícito en cada vueltaAdecuado para proyectos grandes y arriesgadosComplejo; exige experiencia en gestión de riesgos
RADDesarrollo rápido con herramientas y prototipos, plazos cortosRapidezCalidad y escalabilidad
RUP (Rational)Iterativo e incremental, dirigido por casos de uso, centrado en la arquitectura; usa UMLDisciplinado y adaptablePesado

Cuadrantes de la espiral: (1) determinar objetivos, alternativas y restricciones; (2) evaluar alternativas e identificar y resolver riesgos; (3) desarrollar y verificar; (4) planificar la siguiente iteración.

Fases de RUP: inicio (inception), elaboración, construcción y transición, cada una con iteraciones y con disciplinas (modelado del negocio, requisitos, análisis y diseño, implementación, pruebas, despliegue...).

3.3 Métrica versión 3

Métrica v3 es la metodología de planificación, desarrollo y mantenimiento de sistemas de información de la Administración pública española, elaborada por el Consejo Superior de Informática y publicada en 2001 por el entonces Ministerio de Administraciones Públicas. Cubre el desarrollo estructurado y el orientado a objetos y toma como base la norma ISO 12207; también tiene en cuenta ISO/IEC TR 15504 (SPICE), UNE-EN ISO 9001:2000, IEEE 610.12-1990 y metodologías como SSADM, Merise, MAGERIT y Eurométodo.

3.4 Calidad del proceso

  • CMMI: modelo de madurez con 5 niveles (inicial, gestionado, definido, gestionado cuantitativamente, en optimización).

  • ISO/IEC 15504 (SPICE), hoy serie ISO/IEC 330xx: evaluación de procesos.

  • ISO/IEC 25010 (familia SQuaRE): modelo de calidad del producto software (adecuación funcional, eficiencia de desempeño, compatibilidad, usabilidad, fiabilidad, seguridad, mantenibilidad, portabilidad...).

4.2 Scrum (Guía Scrum 2020)

Marco de trabajo ligero de Ken Schwaber y Jeff Sutherland. La Guía Scrum de noviembre de 2020 es la versión vigente. Se basa en el empirismo y el pensamiento lean.

  • Pilares: transparencia, inspección y adaptación.

  • Valores: compromiso, foco, apertura, respeto y coraje.

  • Scrum Team: pequeño, normalmente 10 personas o menos, multifuncional y autogestionado (no «autoorganizado», término de 2017). Sin subequipos ni jerarquías. Desaparece el «equipo de desarrollo».

DevelopersCrean el incremento; elaboran el plan del Sprint (Sprint Backlog) y respetan la Definición de Terminado

4.3 Kanban

Método de flujo de origen lean (Toyota; aplicado al software por David J. Anderson).

  • Tablero con columnas por estado (Por hacer → En curso → Hecho).

  • Limitar el trabajo en curso (WIP) por columna: sistema pull (se tira del trabajo cuando hay capacidad).

  • Sin iteraciones fijas ni roles prescritos; mejora continua del flujo.

  • Métricas: lead time (desde la petición hasta la entrega), cycle time (desde que se empieza a trabajar), throughput, diagrama de flujo acumulado.

4.4 Programación Extrema (XP)

De Kent Beck (finales de los 90). Valores: comunicación, simplicidad, retroalimentación, coraje y respeto.

Prácticas: programación en parejas, TDD, integración continua, refactorización, diseño simple, entregas pequeñas, propiedad colectiva del código, estándares de codificación, cliente in situ, ritmo sostenible (40 horas), juego de la planificación, metáfora.

Otras: Lean Software Development (eliminar desperdicio), Crystal, DSDM, FDD (desarrollo dirigido por funcionalidades).

4.5 DevOps

DevOps une desarrollo (Dev) y operaciones (Ops) mediante cultura, automatización, medición y colaboración (modelo CALMS: cultura, automatización, lean, medición, compartir).

  • Ciclo: planificar → codificar → construir → probar → publicar → desplegar → operar → monitorizar.

  • Infraestructura como código (IaC): Terraform, Ansible, Puppet, Chef.

  • Contenedores (Docker) y orquestación (Kubernetes).

  • Métricas DORA: frecuencia de despliegue, tiempo de entrega de cambios, tasa de fallos en cambios, tiempo de recuperación.

  • DevSecOps: seguridad integrada en toda la cadena.

4.6 CI/CD

PrácticaQué es
Integración continua (CI)Integrar el código en la rama principal varias veces al día; cada integración dispara compilación y pruebas automáticas
Entrega continua (Continuous Delivery)El software está siempre listo para producción; el paso a producción es manual (aprobación)
Despliegue continuo (Continuous Deployment)Cada cambio que supera las pruebas se despliega automáticamente en producción

  • Pipeline (tubería): etapas automatizadas (compilar, pruebas unitarias, análisis estático, empaquetar, desplegar en preproducción, pruebas de aceptación, producción).

  • Herramientas: Jenkins, GitLab CI/CD (.gitlab-ci.yml), GitHub Actions (.github/workflows/*.yml), Azure DevOps, CircleCI; calidad con SonarQube.

  • Estrategias de despliegue: blue-green (dos entornos y se conmuta), canary (a un porcentaje de usuarios), rolling (por lotes), feature flags (interruptores de funcionalidad).

5. Pruebas del software

Probar es ejecutar el software para encontrar defectos; las pruebas muestran la presencia de defectos, no su ausencia (Dijkstra). Norma de referencia: ISO/IEC/IEEE 29119.

5.1 Conceptos básicos

TérminoSignificado
Error (equivocación)Acción humana incorrecta
Defecto (bug, fallo en el código)Imperfección en el producto causada por un error
Fallo (failure)Comportamiento observable incorrecto al ejecutar un defecto
Verificación¿Construimos el producto correctamente? (conforme a la especificación)
Validación¿Construimos el producto correcto? (lo que necesita el usuario)
Caso de pruebaEntradas, condiciones de ejecución y resultado esperado
OráculoMecanismo para saber si el resultado es correcto
DepuraciónLocalizar y corregir el defecto (no es probar)

Pruebas estáticas (sin ejecutar: revisiones, inspecciones, walkthroughs, análisis estático) frente a dinámicas (ejecutando el código).

5.2 Niveles de prueba (modelo en V)

Fase de definiciónNivel de pruebaQué se pruebaQuién
Diseño detallado / códigoUnitariasUn módulo, clase o función aisladosDesarrolladores
Diseño de arquitecturaIntegraciónInterfaces e interacción entre módulosDesarrolladores / equipo de pruebas
Análisis de requisitos del sistemaSistemaEl sistema completo, requisitos funcionales y no funcionalesEquipo de pruebas
Requisitos del usuarioAceptaciónQue cumple las necesidades del usuarioUsuario / cliente

En Métrica v3 las unitarias, de integración y de sistema se ejecutan en CSI; las de implantación y aceptación, en IAS; el plan de pruebas se especifica en ASI.

Estrategias de integración

  • Big bang: todo a la vez (difícil localizar fallos).

  • Descendente (top-down): desde el módulo principal; los inferiores se simulan con stubs (resguardos).

  • Ascendente (bottom-up): desde los módulos inferiores; los superiores se simulan con drivers (conductores).

  • Sandwich: combinación.

Pruebas de aceptación: alfa (por usuarios en el entorno del desarrollador) y beta (por usuarios en su propio entorno).

5.3 Técnicas de diseño de casos

Complejidad ciclomática V(G) = aristas − nodos + 2 = número de decisiones + 1 = número de regiones del grafo. Indica el número de caminos independientes (casos mínimos para cubrir el camino básico).

Ejemplo de valores límite: si la edad válida es 18-65, se prueban 17, 18, 65 y 66 (y a veces 19 y 64). Particiones de equivalencia: <18 (no válida), 18-65 (válida), >65 (no válida).

5.5 TDD, BDD y automatización

  • TDD (Test-Driven Development, Kent Beck): ciclo rojo → verde → refactorizar: (1) escribir una prueba que falla; (2) escribir el código mínimo para que pase; (3) mejorar el código manteniendo las pruebas en verde.

  • BDD (Behavior-Driven Development): escenarios en lenguaje natural con Gherkin: Given / When / Then (Dado / Cuando / Entonces); herramienta Cucumber.

  • ATDD: pruebas de aceptación definidas antes de desarrollar.

  • Dobles de prueba: dummy, stub (respuestas predefinidas), fake, mock (verifica las llamadas recibidas), spy.

  • Pirámide de pruebas (Mike Cohn): muchas unitarias en la base, menos de integración/servicio y pocas de interfaz de usuario (end-to-end) en la cima.

  • Cobertura de código: porcentaje de código ejecutado por las pruebas (JaCoCo, Istanbul).

6. Programas para control de versiones

Un sistema de control de versiones (VCS) registra los cambios de los ficheros en el tiempo: permite recuperar versiones anteriores, saber quién cambió qué y cuándo, trabajar en paralelo con ramas y fusionar el trabajo.

6.1 Tipos y herramientas

TipoRasgosHerramientas
LocalVersiones en el propio equipoRCS, SCCS
Centralizado (CVCS)Un servidor con el repositorio; los clientes tienen una copia de trabajo; requiere conexión para commit e historialCVS, Subversion (SVN), Perforce, TFVC
Distribuido (DVCS)Cada clon tiene el repositorio completo con todo el historial; se trabaja sin conexión; no hay un único punto de falloGit, Mercurial, Bazaar

  • Git: creado por Linus Torvalds en 2005 para el núcleo Linux (tras dejar BitKeeper). Libre (GPLv2). Guarda instantáneas (snapshots), no diferencias.

  • Subversion (SVN): creado en 2000 por CollabNet como sucesor de CVS; hoy proyecto Apache. Numeración de revisiones global y secuencial (r1, r2...); commits atómicos; versiona directorios.

6.2 Subversion: comandos

6.4 Merge frente a rebase

git mergegit rebase
Qué haceUne dos ramas creando un commit de fusión (con dos padres), salvo fast-forwardReescribe los commits de la rama sobre la punta de otra
HistorialConserva la historia real, no linealLineal y limpio
RiesgoNinguno sobre la historia existenteCambia los hashes: no rebasar ramas ya publicadas y compartidas
Uso típicoIntegrar ramas de funcionalidadActualizar una rama local antes de integrarla; rebase -i para reordenar o combinar (squash)

  • Fast-forward: si la rama destino no ha avanzado, merge solo mueve el puntero, sin commit de fusión (--no-ff lo fuerza).

  • Squash merge: combina todos los commits de la rama en uno.

  • Conflicto: cambios incompatibles en las mismas líneas. Git marca el fichero con <<<<<<<, ======= y >>>>>>>; se edita, se hace git add y se completa con git commit (o git rebase --continue).

Buenas prácticas: commits pequeños y frecuentes, mensajes claros (convención Conventional Commits: feat:, fix:, docs:), no versionar secretos ni binarios generados (.gitignore), revisión de código antes de integrar. Para ficheros grandes: Git LFS.

7. Plataformas de desarrollo colaborativo de software

Una plataforma de desarrollo colaborativo (forja de software) combina el alojamiento de repositorios con herramientas para que muchos desarrolladores trabajen juntos: revisión de código, gestión de incidencias, documentación, integración continua y control de permisos.

7.1 Principales plataformas

PlataformaRasgos
GitHubLanzada en 2008; propiedad de Microsoft desde 2018. Pull requests, Issues, Actions (CI/CD), Pages, Codespaces, Copilot, Dependabot. La mayor comunidad de código abierto
GitLabPlataforma DevOps completa en una sola aplicación; modelo open core (edición libre instalable en servidores propios). Merge requests, GitLab CI/CD integrada, registro de contenedores
BitbucketDe Atlassian; integración con Jira y Confluence; Bitbucket Pipelines
Azure DevOpsMicrosoft: Repos, Boards, Pipelines, Test Plans, Artifacts
Gitea / ForgejoLigeras, libres y autoalojables
SourceForgeHistórica (1999), proyectos de código abierto

Flujo típico de contribución (fork & pull): fork → git clone → rama nueva → commits → git push a su fork → abrir pull request → revisión y CI → merge por un mantenedor.

7.3 Herramientas complementarias

  • Gestión de proyectos e incidencias: Jira, Redmine, Trello.

  • Documentación: Confluence, wikis.

  • Comunicación: Microsoft Teams, Slack, Mattermost.

  • Revisión de código dedicada: Gerrit.

  • Desarrollo en la nube: entornos remotos (Codespaces, Gitpod).

7.4 Colaboración en el sector público

  • Ley 40/2015, de Régimen Jurídico del Sector Público: art. 157 (las Administraciones pondrán a disposición de otras las aplicaciones de su propiedad para su reutilización, y antes de desarrollar una nueva deben consultar si existen soluciones reutilizables) y art. 158 (transferencia de tecnología: directorios actualizados de aplicaciones reutilizables).

  • Centro de Transferencia de Tecnología (CTT) del Portal de Administración Electrónica (PAe): directorio de soluciones y forja para compartir código entre Administraciones.

  • Licencias de código abierto habituales: EUPL (European Union Public Licence, de la Comisión Europea), GPL (copyleft), Apache 2.0 y MIT (permisivas).

  • En la UE, el repositorio code.europa.eu aloja código abierto de instituciones europeas.

Esquema de repaso

  • Repositorio = almacén controlado con metadatos e historial: de código (Git, SVN), de artefactos (Maven Central, npm, Nexus), CASE (núcleo integrado de la herramienta).

  • SVN: trunk, branches, tags; revisiones globales y commits atómicos. Git: directorio de trabajo, índice, repositorio local y remoto; objetos blob, tree, commit y tag.

  • Maven: coordenadas groupId:artifactId:version; repositorio local ~/.m2. SemVer MAYOR.MENOR.PARCHE.

  • Concurrencia: bloquear-modificar-desbloquear frente a copiar-modificar-fusionar. Línea base = configuración aprobada.

  • CASE: Upper (análisis), Lower (código y pruebas), I-CASE (todo el ciclo). Ingeniería directa, inversa y de ida y vuelta; MDA: CIM → PIM → PSM.

  • Documentación: Javadoc (/** */, @param, @return, @throws), Doxygen, Sphinx, JSDoc.

  • OpenAPI = especificación de API REST en YAML/JSON (antes Swagger); Swagger = herramientas (Swagger UI). WSDL para SOAP; AsyncAPI para eventos.

  • Cascada (Royce, 1970) secuencial; en V asocia fases y pruebas; espiral (Boehm) = análisis de riesgos; incremental = entregas parciales; RUP: inicio, elaboración, construcción, transición.

  • Métrica v3 (2001): PSI; EVS, ASI, DSI, CSI, IAS; MSI (solo correctivo y evolutivo). Interfaces: GP, SEG, GC, CAL.

  • Manifiesto ágil (2001, 4 valores y 12 principios). Scrum 2020: PO, Scrum Master, Developers; equipo autogestionado de 10 o menos. Sprint ≤ 1 mes; Planning 8 h, Daily 15 min, Review 4 h, Retro 3 h.

  • Compromisos: Product Backlog → Product Goal; Sprint Backlog → Sprint Goal; Incremento → Definition of Done. Solo el PO cancela un Sprint.

  • Kanban: tablero, límite WIP, sistema pull, sin iteraciones; lead time y cycle time. XP (Kent Beck): parejas, TDD, CI, refactorización.

  • DevOps (CALMS, IaC, métricas DORA). CI = integrar y probar a menudo; entrega continua = paso a producción manual; despliegue continuo = automático.

  • Verificación = producto correctamente; validación = producto correcto. Error → defecto → fallo.

  • Niveles: unitarias, integración (stubs descendente, drivers ascendente), sistema, aceptación (alfa y beta).

  • Caja blanca = código (coberturas, McCabe V(G) = aristas − nodos + 2); caja negra = especificación (particiones, valores límite). Regresión = no romper lo anterior; estrés = más allá de los límites.

  • TDD: rojo → verde → refactorizar. BDD con Gherkin (Given/When/Then). Pirámide: muchas unitarias.

  • Git (Torvalds, 2005) distribuido; SVN (2000, Apache) centralizado. fetch descarga sin integrar; pull = fetch + merge; revert deshace con un commit nuevo; reset --hard descarta.

  • merge conserva la historia (commit de fusión); rebase la reescribe en línea (no en ramas compartidas). Git Flow, GitHub Flow, trunk-based.

  • Plataformas: GitHub (Microsoft), GitLab (DevOps completo, autoalojable), Bitbucket (Atlassian). Fork, pull/merge request, issues. Ley 40/2015 arts. 157-158 y CTT; licencia EUPL.
