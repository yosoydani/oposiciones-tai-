1. El modelo cliente/servidor

En el modelo cliente/servidor (C/S) la aplicación se reparte entre procesos que piden servicios (clientes) y procesos que los prestan (servidores), comunicados por una red mediante un protocolo de petición/respuesta. El cliente siempre inicia la comunicación; el servidor espera peticiones de forma pasiva.

1.1. Componentes

ComponenteFunción
Cliente (front-end)Inicia peticiones, presenta la información, interactúa con el usuario
Servidor (back-end)Espera peticiones, las procesa y devuelve respuestas; gestiona recursos compartidos
MiddlewareCapa de software intermedia que oculta la heterogeneidad de red, SO y lenguajes (sec. 3)
Red y protocolosTransporte (TCP/IP) y protocolo de aplicación (HTTP, SQL*Net, SMB…)

1.2. Características

  • Separación de funciones entre petición y servicio; centralización de datos y control en el servidor.

  • Recursos compartidos: varios clientes usan el mismo servidor de forma concurrente.

  • Transparencia de ubicación: el cliente no necesita saber dónde está físicamente el servidor.

  • Escalabilidad horizontal (más servidores) y vertical (servidor más potente).

  • Heterogeneidad: cliente y servidor pueden usar plataformas distintas.

  • Encapsulación de servicios: el servidor ofrece una interfaz; su implementación puede cambiar sin afectar al cliente.

1.3. Ventajas e inconvenientes

VentajasInconvenientes
Control centralizado de datos, seguridad y copiasEl servidor es un punto único de fallo y posible cuello de botella
Mantenimiento más sencillo (cambios en el servidor)Congestión de red con muchos clientes
Escalabilidad y reparto de cargaCoste de servidores y de administración
Integración de plataformas heterogéneasDependencia de la red: sin conexión no hay servicio

1.4. Tipos de servidor y modelos alternativos

  • Por el servicio: de ficheros, de bases de datos, de aplicaciones, web, de correo, de impresión, de nombres (DNS), de directorio (LDAP).

  • Servidor iterativo (atiende una petición cada vez) frente a concurrente (un hilo/proceso por petición o un pool); con estado (stateful, recuerda la sesión) frente a sin estado (stateless, como HTTP o REST: escala mejor).

  • Peer-to-peer (P2P): todos los nodos son a la vez cliente y servidor (BitTorrent, blockchain); sin servidor central.

  • Modelo de Gartner (1995): clasifica el reparto de las tres funciones (presentación, lógica, datos) entre cliente y servidor en cinco modelos: presentación distribuida, presentación remota, lógica distribuida, gestión de datos remota y base de datos distribuida.

  • Computación en la nube: el servidor se sustituye por servicios gestionados (IaaS, PaaS, SaaS); serverless / FaaS: funciones que se ejecutan bajo demanda.

2. Arquitecturas en capas: 2, 3 y n capas

Toda aplicación tiene tres capas lógicas (layers): presentación, lógica de negocio y datos. Los niveles físicos (tiers) indican en cuántas máquinas o procesos se despliegan. En test se usa “capa” para ambos, pero conviene distinguir layer (lógica) de tier (física).

2.1. Capas lógicas

CapaResponsabilidadEjemplos
PresentaciónInterfaz de usuario, captura y validación básica de datosHTML/JS en navegador, JSF, Razor, app móvil
Negocio (lógica de aplicación)Reglas de negocio, procesos, cálculos, transaccionesEJB, beans CDI, servicios Spring, servicios ASP.NET Core
Datos (persistencia)Almacenamiento y acceso a datosSGBD (Oracle, PostgreSQL, SQL Server), DAO/JPA

2.2. Comparativa de niveles

ArquitecturaRepartoVentajasInconvenientes
1 nivel (monolítica / mainframe con terminales tontos)Todo en una máquinaSencilla, control totalNo escala, no comparte
2 niveles (C/S clásico)Cliente (presentación + a menudo lógica) ↔ servidor de BD (datos y procedimientos almacenados)Desarrollo rápido (Visual Basic, PowerBuilder, Forms), adecuada para pocos usuariosEscalabilidad limitada (una conexión por cliente), distribución costosa de actualizaciones a cada cliente, lógica dispersa

Variantes de 2 niveles según dónde va la lógica: cliente pesado (lógica en el cliente) o servidor pesado (lógica en procedimientos almacenados y triggers del SGBD).

2.3. Cliente ligero, pesado e híbrido

Ligero (thin client)Solo presentación; la lógica está en el servidorNavegador web, terminal VDI, escritorio remotoDespliegue nulo, fácil mantenimiento, menos hardware; depende de la red y del servidor
Pesado / grueso (fat/thick client)Presentación y lógica (y a veces datos locales)Aplicación de escritorio WinForms, Swing, cliente Oracle FormsInterfaz rica, puede trabajar sin conexión, menos carga en servidor; instalación y actualización en cada puesto
Enriquecido / híbrido (rich client, RIA, SPA)Interfaz rica en el navegador con lógica de presentación en JavaScript; datos por APIAngular, React, Vue, Blazor WebAssembly, PWAExperiencia de escritorio sin instalación; más complejidad en el cliente

2.4. Operación de una petición en 3 niveles (web)

  1. El usuario actúa en el navegador; se resuelve el nombre por DNS y se abre conexión TCP (y TLS si es HTTPS).

  2. El navegador envía una petición HTTP (método, URI, cabeceras, cuerpo) al servidor web o al balanceador / proxy inverso.

  3. El servidor web sirve el contenido estático o reenvía al servidor de aplicaciones, que ejecuta la lógica de negocio.

  4. La lógica accede a la base de datos (SQL por JDBC/ADO.NET o un ORM) usando un pool de conexiones, dentro de una transacción.

  5. El servidor de aplicaciones compone la respuesta (HTML o JSON) y devuelve un código de estado HTTP.

  6. El navegador renderiza la respuesta o el código JavaScript actualiza la vista.

Elementos de infraestructura habituales: balanceador de carga (round robin, menos conexiones, hash de IP; sesiones persistentes o sticky), proxy inverso (Nginx, Apache httpd), cachés (Redis, CDN), cortafuegos y DMZ (servidor web en la DMZ, BD en la red interna), API Gateway.

3. Middleware

El middleware es el software que se sitúa entre el sistema operativo/red y las aplicaciones para que componentes distribuidos se comuniquen como si fueran locales, ocultando la heterogeneidad (transparencia de ubicación, de acceso, de fallos, de replicación).

3.1. Tipos de middleware

TipoFuncionamientoEjemplos
De acceso a datosAPI común para distintos SGBDODBC, JDBC, ADO.NET, OLE DB
RPC (Remote Procedure Call)Llamar a un procedimiento remoto como si fuera local; síncronoSun RPC / ONC RPC (con XDR), DCE RPC, XML-RPC, JSON-RPC, gRPC
Orientado a objetos (ORB)Invocación de métodos de objetos remotosCORBA (OMG), Java RMI, DCOM (Microsoft), .NET Remoting
MOM (Message-Oriented Middleware)Intercambio asíncrono de mensajes mediante colas; desacopla emisor y receptor en el tiempoJMS (ActiveMQ), IBM MQ, RabbitMQ (AMQP), Apache Kafka, MQTT
Monitores de transacciones (TP)Coordinan transacciones distribuidasCICS (IBM), Tuxedo (Oracle), estándar X/Open XA
Servidores de aplicacionesContenedor con servicios de transacciones, seguridad, persistenciaJakarta EE, ASP.NET Core
ESB / integraciónEnrutado, transformación y orquestación de serviciosMuleSoft, WSO2, Apache Camel

3.2. RPC

  • El cliente invoca un stub (representante local) que empaqueta los parámetros (marshalling, aplanamiento/serialización) y los envía; en el servidor un skeleton (o stub de servidor) los desempaqueta (unmarshalling), llama al procedimiento real y devuelve el resultado.

  • La interfaz se describe con un IDL (Interface Definition Language) del que se generan stubs y skeletons.

  • Semánticas de fallo: quizás, al menos una vez, como mucho una vez, exactamente una vez (ideal).

3.3. CORBA y RMI

  • CORBA (Common Object Request Broker Architecture, OMG, 1991): independiente de lenguaje y plataforma; ORB como bus de objetos; IDL de OMG; protocolo GIOP y su versión sobre TCP/IP IIOP; servicios de nombres, eventos, transacciones; POA (adaptador de objetos).

  • Java RMI (Remote Method Invocation): objetos remotos solo entre JVM; interfaz que extiende java.rmi.Remote; métodos lanzan RemoteException; registro RMI (rmiregistry, puerto 1099); protocolo JRMP o RMI-IIOP para interoperar con CORBA.

  • DCOM: modelo distribuido de Microsoft sobre COM, solo Windows, hoy obsoleto.

3.4. MOM y protocolos de mensajería

  • Comunicación asíncrona: el emisor no espera; el mensaje queda en la cola aunque el receptor no esté activo (desacoplamiento temporal).

  • Modelos: punto a punto (cola) y publicación/suscripción (tema).

  • Protocolos: AMQP (estándar OASIS e ISO/IEC 19464; RabbitMQ), MQTT (ligero para IoT, OASIS), STOMP (texto), protocolo propio de Kafka (registro distribuido de eventos, alta capacidad, streaming).

  • Garantías de entrega: como mucho una vez, al menos una vez, exactamente una vez; mensajes persistentes y colas de mensajes fallidos (dead letter queue).

4. Arquitectura orientada a servicios (SOA) y microservicios

SOA organiza los sistemas como servicios reutilizables, débilmente acoplados y con contratos estándar, normalmente integrados por un ESB; los microservicios llevan la idea al extremo con servicios pequeños, desplegables de forma independiente y cada uno con sus propios datos.

4.1. Principios de SOA (Thomas Erl)

  • Contrato de servicio estandarizado (WSDL, OpenAPI).

  • Bajo acoplamiento entre proveedor y consumidor.

  • Abstracción: se oculta la implementación.

  • Reutilización de servicios.

  • Autonomía: control sobre su propio entorno.

  • Sin estado (statelessness).

  • Descubrimiento (discoverability): registro y metadatos.

  • Composición (composability): crear servicios a partir de otros.

Roles SOA clásicos: proveedor, consumidor y registro (broker); operaciones: publicar, buscar (find) y enlazar/invocar (bind).

Composición de servicios: orquestación (un coordinador central dirige el proceso, p. ej. WS-BPEL) frente a coreografía (cada servicio reacciona a eventos sin director, p. ej. WS-CDL o arquitecturas de eventos).

ESB (Enterprise Service Bus): bus de integración que ofrece enrutado, transformación de mensajes y protocolos, mediación, seguridad y monitorización. Patrones de referencia: Enterprise Integration Patterns (Hohpe y Woolf).

4.2. Monolito, SOA y microservicios

  • Twelve-Factor App: buenas prácticas para aplicaciones cloud-native (configuración en el entorno, procesos sin estado, paridad desarrollo/producción…).

  • Arquitectura dirigida por eventos (EDA): productores publican eventos en un broker (Kafka) y los consumidores reaccionan.

5. Servicios web SOAP: SOAP, WSDL, UDDI y WS-*

Un servicio web es un sistema software que permite la interoperabilidad máquina a máquina a través de la red mediante protocolos estándar (definición del W3C). La pila clásica “WS-*” se basa en XML: SOAP para los mensajes, WSDL para describir la interfaz y UDDI para publicarla y descubrirla.

5.3. WSDL

Documento XML que describe qué hace el servicio (operaciones y mensajes), cómo se invoca (protocolo y formato) y dónde está (URL).

  • Parte abstracta (types, message, portType/interface) y parte concreta (binding, port/endpoint, service).

Estructuras: businessEntity, businessService, bindingTemplate, tModel. Los registros públicos UBR de IBM, Microsoft y SAP cerraron en 2006; hoy se usan registros privados o catálogos de API.

6. REST y HTTP

REST (Representational State Transfer) es un estilo arquitectónico, no un protocolo ni un estándar, definido por Roy Fielding en su tesis doctoral (2000). Modela el sistema como recursos identificados por URI que se manipulan mediante representaciones (JSON, XML, HTML) con los métodos uniformes de HTTP.

6.1. Restricciones REST

  1. Cliente-servidor: separación de responsabilidades.

  2. Sin estado (stateless): cada petición lleva toda la información necesaria; el servidor no guarda sesión.

  3. Cacheable: las respuestas indican si pueden almacenarse en caché.

  4. Interfaz uniforme: identificación de recursos por URI, manipulación mediante representaciones, mensajes autodescriptivos y HATEOAS (Hypermedia As The Engine Of Application State: la respuesta incluye enlaces a las acciones posibles).

  5. Sistema en capas: el cliente no sabe si habla con el servidor final o con un intermediario (proxy, caché, gateway).

  6. Código bajo demanda (code on demand): la única opcional; el servidor puede enviar código ejecutable (JavaScript).

Modelo de madurez de Richardson: nivel 0 (un único endpoint, estilo RPC/POX), nivel 1 (recursos), nivel 2 (verbos HTTP y códigos de estado), nivel 3 (HATEOAS). Solo el nivel 3 es REST “pleno” según Fielding.

  • Seguro: no modifica el estado del servidor. Idempotente: repetir la petición N veces produce el mismo efecto que hacerla una vez. Todo método seguro es idempotente, pero no al revés (PUT y DELETE son idempotentes, no seguros).

6.5. OpenAPI

  • OpenAPI Specification (OAS): formato estándar, en YAML o JSON, para describir APIs REST/HTTP (rutas, operaciones, parámetros, esquemas, seguridad); papel equivalente al WSDL en SOAP. Lo gestiona la OpenAPI Initiative (Linux Foundation); procede de Swagger (donado por SmartBear en 2015).

  • Versiones: 2.0 (= Swagger 2.0), 3.0, 3.1 (alineada con JSON Schema), 3.2.0 (septiembre de 2025) y 3.2.1 (10/09/2026), la última publicada. Fuente: OpenAPI Specification v3.2.

  • Herramientas: Swagger UI (documentación interactiva), Swagger Editor, generadores de código (OpenAPI Generator). AsyncAPI es el equivalente para APIs asíncronas y dirigidas por eventos.

openapi: 3.1.0

        '404': { description: No existe }

7. Otras tecnologías y formatos: GraphQL, gRPC, WebSocket

Junto a SOAP y REST, las API modernas usan GraphQL (consultas flexibles definidas por el cliente), gRPC (RPC binario de alto rendimiento) y WebSocket (canal bidireccional persistente).

7.1. GraphQL

  • Lenguaje de consulta y entorno de ejecución para API, creado por Facebook (uso interno desde 2012, publicado en 2015); hoy lo gobierna la GraphQL Foundation (Linux Foundation).

  • Un único endpoint (normalmente POST /graphql); el cliente pide exactamente los campos que necesita: evita la sobrecarga (over-fetching) y la subcarga (under-fetching) de REST.

  • Esquema fuertemente tipado (SDL) con tres tipos de operación: query (lectura), mutation (escritura) y subscription (notificaciones en tiempo real, normalmente por WebSocket). Funciones resolver obtienen cada campo.

  • Introspección: el esquema puede consultarse a sí mismo.

  • Inconvenientes: caché HTTP más difícil (todo POST a un endpoint), riesgo de consultas muy costosas (limitar profundidad y complejidad), problema N+1 (DataLoader).

  • Especificación: edición de octubre de 2021 y nueva edición de septiembre de 2025 (añade OneOf input objects, schema coordinates, más deprecaciones, Unicode completo). Fuente: GraphQL, September 2025 Edition.

query {
  expediente(id: "2026/001") {
    asunto
    titular { nombre }
  }
}

7.2. gRPC

  • Framework RPC de código abierto creado por Google (publicado en 2015), proyecto de la CNCF.

  • Transporte HTTP/2 (multiplexación, binario) y serialización con Protocol Buffers (protobuf): formato binario, compacto y rápido; el contrato se define en ficheros .proto (IDL) de los que se genera código cliente y servidor en muchos lenguajes.

  • Cuatro tipos de llamada: unaria (petición-respuesta), streaming del servidor, streaming del cliente y streaming bidireccional.

  • Uso típico: comunicación interna entre microservicios de baja latencia. Limitación: el navegador no lo usa directamente (requiere gRPC-Web y un proxy).

syntax = "proto3";
service Expedientes {
  rpc Consultar (ConsultaRequest) returns (Expediente);
}
message ConsultaRequest { string id = 1; }
message Expediente { string id = 1; string asunto = 2; }

8. Seguridad en servicios web y uso en la Administración

La seguridad de un servicio web se aplica en dos niveles: transporte (TLS cifra el canal punto a punto) y mensaje (WS-Security o tokens firmados protegen el contenido extremo a extremo, aunque pase por intermediarios).

8.2. Amenazas y buenas prácticas

  • OWASP API Security Top 10 (edición 2023): encabezado por la autorización rota a nivel de objeto (BOLA); incluye autenticación rota, consumo de recursos sin restricciones, SSRF, inventario deficiente de API, etc.

  • Validar entradas (esquemas XSD, JSON Schema) frente a inyección; en SOAP/XML, desactivar entidades externas frente a XXE y limitar tamaño frente a XML bombs.

  • Limitación de tráfico (rate limiting, respuesta 429), cuotas y API Gateway con autenticación centralizada.

  • CORS restringido a orígenes de confianza; cabeceras de seguridad (HSTS).

  • Registro y trazabilidad de accesos (auditoría), exigida por el ENS.

8.3. Servicios web en la Administración General del Estado

  • Ley 40/2015 (art. 155): las administraciones deben facilitar el acceso de otras a los datos de los interesados que obren en su poder; Ley 39/2015 (art. 28): el ciudadano no está obligado a aportar documentos que ya tenga la Administración.

  • Plataforma de Intermediación de Datos (PID): intercambio de certificados y datos entre organismos (identidad, residencia, estar al corriente con Hacienda y Seguridad Social…) mediante servicios web SOAP según el protocolo SCSP (Sustitución de Certificados en Soporte Papel), con firma WS-Security.

  • Red SARA: red privada que interconecta las administraciones y sus servicios comunes.

  • Cl@ve (identificación del ciudadano, basada en SAML 2.0), @firma (validación de certificados y firmas), Notific@, SIR (registro).

  • Marco normativo: ENS (RD 311/2022) para la seguridad y ENI (RD 4/2010) para la interoperabilidad (normas técnicas como la de protocolos de intermediación de datos).

Esquema de repaso

  • C/S: el cliente inicia la petición; el servidor espera, procesa y responde.

  • Componentes: cliente (front-end), servidor (back-end), middleware, red y protocolos.

  • Inconvenientes de C/S: servidor como punto único de fallo y cuello de botella; congestión de red.

  • Capas lógicas (layers): presentación, negocio y datos; niveles físicos (tiers): dónde se despliegan.

  • 2 niveles: cliente ↔ BD; escala mal. 3 niveles: cliente ↔ servidor de aplicaciones ↔ BD; escala y centraliza la lógica.

  • Cliente ligero = solo presentación (navegador); pesado = presentación + lógica, instalado en cada puesto.

  • Gartner: 5 modelos de reparto (presentación distribuida, presentación remota, lógica distribuida, gestión de datos remota, BD distribuida).

  • Middleware: acceso a datos (ODBC/JDBC), RPC, ORB (CORBA, RMI), MOM (colas, asíncrono), monitores TP.

  • RPC: stub y skeleton, marshalling, IDL. CORBA usa IIOP; RMI, registro en el puerto 1099.

  • SOA: proveedor, consumidor, registro; publicar, buscar, enlazar; ESB; orquestación (BPEL) frente a coreografía.

  • Microservicios: pequeños, despliegue independiente, una BD por servicio, API Gateway, circuit breaker, Saga, CQRS.

  • Pila SOAP: SOAP (mensaje), WSDL (descripción), UDDI (registro), sobre XML y HTTP.

  • SOAP: Envelope y Body obligatorios, Header opcional, Fault para errores; 1.2 usa application/soap+xml.

  • WSDL 1.1 → 2.0: portType → interface, port → endpoint, desaparece message.

  • WS-Security: firma y cifrado XML a nivel de mensaje; WS-I Basic Profile recomienda document/literal.

  • REST (Fielding, 2000): estilo, no protocolo; restricciones: C/S, sin estado, caché, interfaz uniforme (HATEOAS), capas, código bajo demanda (opcional).

  • Verbos: GET (seguro e idempotente), POST (ni seguro ni idempotente), PUT y DELETE (idempotentes), PATCH (parcial, no idempotente).

  • Códigos: 201 creado, 204 sin contenido, 304 no modificado, 401 no autenticado, 403 prohibido, 404, 409 conflicto, 429, 500, 503.

  • OpenAPI (antes Swagger) describe API REST en YAML/JSON; versión 3.2; GraphQL: un endpoint, query/mutation/subscription; gRPC: HTTP/2 + Protocol Buffers, 4 tipos de llamada.

  • Seguridad: TLS/mTLS, OAuth 2.0 autoriza, OpenID Connect autentica, JWT; en la AGE, PID/SCSP (SOAP), Red SARA, Cl@ve (SAML 2.0).
