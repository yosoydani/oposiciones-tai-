1. Plataformas de desarrollo empresarial: visión general

Jakarta EE (antes Java EE) y .NET son las dos grandes plataformas para aplicaciones empresariales multicapa: ofrecen un entorno de ejecución gestionado, un modelo de componentes y servicios comunes (transacciones, seguridad, persistencia, mensajería, servicios web) para que el desarrollador se centre en la lógica de negocio.

2. Jakarta EE: evolución, perfiles y arquitectura

Jakarta EE es un conjunto de especificaciones que amplía Java SE con APIs empresariales; las aplicaciones se despliegan en un servidor de aplicaciones que proporciona contenedores con servicios gestionados.

2.1. Evolución de nombres y versiones

  • El motivo del cambio de nombre: Oracle conservó la marca “Java” y el espacio javax, de modo que la Eclipse Foundation no podía evolucionar las APIs bajo javax. Todas las aplicaciones de Java EE 8 deben migrar sus import javax.servlet... a import jakarta.servlet... (herramientas como Eclipse Transformer o OpenRewrite automatizan la migración).

  • Ojo: no todo javax cambia. Los paquetes de Java SE siguen siendo javax (javax.sql, javax.swing, javax.crypto); solo cambian los de la plataforma empresarial.

  • Las especificaciones se gestionan con el Jakarta EE Specification Process (JESP), que sustituye al JCP (Java Community Process) y a sus JSR. Cada especificación tiene API, documento y TCK (Technology Compatibility Kit); un producto es “compatible” si supera el TCK.

Fuente del cambio de espacio de nombres: Jakarta EE Working Group, 8/12/2020.

3. Componentes de Jakarta EE

Los componentes se reparten por capas: Servlets, JSP y JSF en la web; CDI y EJB en negocio; JAX-RS, WebSocket y JMS para integración. Desde Jakarta EE 9 las especificaciones se llaman Jakarta X (Jakarta Servlet, Jakarta Faces…), aunque en test siguen apareciendo los nombres clásicos.

3.2. Servlets

  • Clase que extiende HttpServlet y sobrescribe doGet(), doPost(), doPut(), doDelete().

  • Ciclo de vida, gestionado por el contenedor: init() (una vez) → service() (por cada petición, despacha a doXxx) → destroy() (una vez). Una única instancia atiende peticiones concurrentes en hilos distintos: no debe guardar estado en atributos.

  • Objetos clave: HttpServletRequest, HttpServletResponse, HttpSession (sesión de usuario, por cookie JSESSIONID o reescritura de URL), ServletContext (ámbito de aplicación), RequestDispatcher (forward e include; sendRedirect hace redirección en el cliente).

  • Filtros (Filter, @WebFilter): interceptan peticiones y respuestas (autenticación, registro, compresión). Listeners: eventos de ciclo de vida.

  • Contenedores de servlets “ligeros”: Apache Tomcat, Jetty, Undertow.

@WebServlet("/expedientes")
public class ExpedienteServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws IOException {
        resp.setContentType("text/plain");
        resp.getWriter().println("Expediente: " + req.getParameter("id"));
    }
}

3.3. JSP y JSF

  • JSP: página HTML con directivas <%@ page %>, scriptlets <% %>, expresiones <%= %>, declaraciones <%! %>, acciones <jsp:include>, EL ${} y etiquetas JSTL. El contenedor la traduce a un servlet y la compila la primera vez. Objetos implícitos: request, response, session, application, out, pageContext, config, page, exception.

  • JSF (Jakarta Faces): framework MVC basado en componentes y eventos. Controlador: FacesServlet (Front Controller). Vistas: Facelets (.xhtml, desde JSF 2.0 sustituye a JSP). Modelo: beans CDI (@Named) enlazados con EL #{bean.propiedad}.

  • Ciclo de vida JSF (6 fases): 1) Restaurar vista, 2) Aplicar valores de la petición, 3) Procesar validaciones, 4) Actualizar valores del modelo, 5) Invocar la aplicación, 6) Renderizar la respuesta.

  • Bibliotecas de componentes: PrimeFaces, OmniFaces. Implementaciones: Mojarra (referencia) y MyFaces (Apache).

  • Jakarta MVC: framework MVC orientado a acciones sobre JAX-RS (no forma parte de la plataforma).

3.4. CDI

  • Inyección con @Inject; nombre accesible desde EL con @Named.

  • Ámbitos (scopes): @RequestScoped, @SessionScoped, @ApplicationScoped, @ConversationScoped, @Dependent (por defecto).

  • Cualificadores (@Qualifier), productores (@Produces), interceptores (@Interceptor, @AroundInvoke), decoradores, eventos (Event<T>, @Observes).

  • Fichero opcional beans.xml. CDI Lite (Core Profile) permite resolución en compilación.

3.5. EJB (Jakarta Enterprise Beans)

TipoAnotaciónEstadoUso

  • Los entity beans de EJB 2.x fueron sustituidos por las entidades JPA (Java EE 5) y eliminados de la especificación.

  • Vistas de cliente: @Local, @Remote (acceso por RMI-IIOP desde otra JVM) y no-interface view. Servicios: transacciones declarativas (@TransactionAttribute), seguridad (@RolesAllowed), temporizadores (@Schedule), métodos asíncronos (@Asynchronous).

  • EJB Lite: subconjunto en el Web Profile (sin MDB ni interfaces remotas).

3.6. JAX-RS (Jakarta REST)

@Path("/expedientes")
@Produces(MediaType.APPLICATION_JSON)
public class ExpedienteResource {
    @Inject ServicioExpedientes servicio;

    @GET @Path("/{id}")
    public Expediente obtener(@PathParam("id") String id) { return servicio.buscar(id); }

    @POST @Consumes(MediaType.APPLICATION_JSON)
    public Response crear(Expediente e) { servicio.alta(e); return Response.status(201).build(); }
}

Anotaciones: @Path, @GET, @POST, @PUT, @DELETE, @PATCH, @PathParam, @QueryParam, @HeaderParam, @FormParam, @Produces, @Consumes. Implementaciones: Jersey (referencia), RESTEasy (Red Hat), Apache CXF.

3.7. JMS (Jakarta Messaging)

  • Mensajería asíncrona y débilmente acoplada a través de un proveedor (MOM): ActiveMQ Artemis, IBM MQ, RabbitMQ (con puente).

  • Dos modelos: punto a punto (cola, Queue: un mensaje lo consume un solo receptor) y publicación/suscripción (tema, Topic: lo reciben todos los suscriptores; suscripciones duraderas).

  • Partes del mensaje: cabecera (JMSMessageID, JMSDestination, JMSDeliveryMode, JMSPriority...), propiedades y cuerpo (TextMessage, ObjectMessage, BytesMessage, MapMessage, StreamMessage).

  • Modos de entrega: PERSISTENT (sobrevive a caídas) y NON_PERSISTENT.

4. Persistencia en Java

La persistencia en Java tiene dos niveles: JDBC, API de bajo nivel para ejecutar SQL, y JPA (Jakarta Persistence), ORM estándar que mapea clases a tablas. Jakarta EE 11 añade Jakarta Data, un nivel de repositorios sobre JPA o bases NoSQL.

4.1. JDBC

  • API de Java SE (java.sql, javax.sql): no cambió de espacio de nombres.

  • Secuencia: cargar el driver → DriverManager.getConnection() o, en servidor, DataSource obtenido por JNDI (pool de conexiones) → Statement / PreparedStatement (precompilada, con parámetros ?, evita la inyección SQL) / CallableStatement (procedimientos almacenados) → ResultSet → cerrar recursos (try-with-resources).

  • executeQuery() (SELECT, devuelve ResultSet), executeUpdate() (INSERT/UPDATE/DELETE, devuelve nº de filas), execute().

  • Tipos de driver JDBC: tipo 1 (puente JDBC-ODBC, eliminado en Java 8), tipo 2 (API nativa), tipo 3 (protocolo de red con middleware), tipo 4 (Java puro, protocolo nativo de la BD; el habitual).

  • Transacciones: setAutoCommit(false), commit(), rollback(), niveles de aislamiento (TRANSACTION_READ_COMMITTED, SERIALIZABLE…).

4.2. JPA (Jakarta Persistence)

ElementoDescripción
EntidadClase con @Entity, clave primaria @Id (@GeneratedValue), constructor sin argumentos; @Table, @Column, @Transient
EntityManagerInterfaz principal: persist(), find(), merge(), remove(), createQuery(), flush()
Contexto de persistenciaConjunto de entidades gestionadas; garantiza una instancia por identidad
Unidad de persistenciaConfiguración en persistence.xml (fuente de datos, proveedor, clases)
JPQLLenguaje de consultas sobre entidades, no tablas: SELECT e FROM Expediente e WHERE e.estado = :est
Criteria APIConsultas con tipado seguro construidas en código
ProveedoresHibernate (Red Hat), EclipseLink (referencia), Apache OpenJPA

  • Relaciones: @OneToOne, @OneToMany, @ManyToOne, @ManyToMany; mappedBy indica el lado no propietario; carga FetchType.LAZY (perezosa; por defecto en *ToMany) o EAGER (ansiosa; por defecto en *ToOne); cascada CascadeType.PERSIST, MERGE, REMOVE, ALL.

  • Herencia (@Inheritance): SINGLE_TABLE (por defecto, una tabla con columna discriminadora), JOINED (tabla por clase unida por clave), TABLE_PER_CLASS. @MappedSuperclass para atributos comunes sin entidad.

  • Estados de una entidad: nueva (new/transient), gestionada (managed), separada (detached) y eliminada (removed).

  • Problema N+1: una consulta para la lista y N para las relaciones perezosas; se resuelve con JOIN FETCH o grafos de entidad.

  • Bloqueo optimista con @Version; pesimista con LockModeType.PESSIMISTIC_WRITE.

@Entity
public class Expediente {
    @Id @GeneratedValue private Long id;
    private String asunto;
    @ManyToOne(fetch = FetchType.LAZY) private Ciudadano titular;
    @OneToMany(mappedBy = "expediente", cascade = CascadeType.ALL)
    private List<Documento> documentos;
}

@Stateless
public class ExpedienteDAO {
    @PersistenceContext EntityManager em;
    public void alta(Expediente e) { em.persist(e); }   // transacción gestionada por el contenedor
}

4.3. Jakarta Data (nuevo en Jakarta EE 11)

Repositorios declarativos: se escribe una interfaz con @Repository que extiende CrudRepository o BasicRepository y el proveedor genera la implementación. Incluye paginación por desplazamiento y por cursor y un lenguaje de consulta propio (JDQL, subconjunto de JPQL). Idea equivalente a Spring Data.

4.4. Transacciones (JTA)

  • ACID: atomicidad, consistencia, aislamiento, durabilidad. JTA coordina transacciones distribuidas con confirmación en dos fases (2PC, recursos XA).

  • CMT (gestionadas por el contenedor, declarativas) frente a BMT (gestionadas por el bean, UserTransaction). En CDI: @Transactional.

  • Atributos de propagación (@TransactionAttribute / @Transactional(TxType)): REQUIRED (por defecto: se une a la existente o crea una), REQUIRES_NEW (siempre una nueva, suspende la actual), MANDATORY (exige una existente, si no excepción), SUPPORTS, NOT_SUPPORTED, NEVER (excepción si hay transacción).

5. Seguridad en Jakarta EE

Jakarta EE ofrece seguridad declarativa (anotaciones o descriptores, la aplica el contenedor) y programática (el código consulta la identidad), basada en roles: el desarrollador declara roles lógicos y el despliegue los asocia a usuarios y grupos reales.

5.1. Conceptos

ConceptoSignificado
AutenticaciónComprobar quién es el usuario
AutorizaciónComprobar qué puede hacer (control de acceso por roles, RBAC)
PrincipalIdentidad autenticada (java.security.Principal)
RolAgrupación lógica de permisos (ADMIN, TRAMITADOR)
Realm / almacén de identidadesBase de usuarios, credenciales y grupos (BD, LDAP, fichero)
Confidencialidad e integridadCifrado del transporte con TLS (HTTPS)

5.2. Mecanismos

  • Seguridad declarativa en la capa web (web.xml o anotaciones): <security-constraint> con <web-resource-collection> (URL y métodos), <auth-constraint> (roles) y <user-data-constraint> con CONFIDENTIAL (fuerza HTTPS). Anotaciones @ServletSecurity, @HttpConstraint.

  • Métodos de autenticación HTTP (<login-config>): BASIC (usuario:contraseña en Base64; solo con TLS), DIGEST, FORM (formulario propio con j_security_check, j_username, j_password) y CLIENT-CERT (certificado X.509 del cliente, autenticación mutua TLS; el caso del DNIe y certificados de la FNMT).

  • Anotaciones de autorización (Jakarta Annotations): @RolesAllowed({"ADMIN"}), @PermitAll, @DenyAll, @DeclareRoles, @RunAs.

  • Programática: request.isUserInRole("ADMIN"), request.getUserPrincipal(), SessionContext.isCallerInRole(), o SecurityContext de Jakarta Security.

  • Jakarta Security (desde Java EE 8): API portable con HttpAuthenticationMechanism (incluye @BasicAuthenticationMechanismDefinition, @FormAuthenticationMechanismDefinition, @CustomFormAuthenticationMechanismDefinition y, desde Jakarta Security 3.0 / EE 10, @OpenIdAuthenticationMechanismDefinition para OpenID Connect), IdentityStore (@DatabaseIdentityStoreDefinition, @LdapIdentityStoreDefinition) y SecurityContext.

  • Jakarta Authentication (antes JASPIC) y Jakarta Authorization (antes JACC): contratos de bajo nivel entre el contenedor y proveedores de seguridad.

  • MicroProfile JWT: autenticación por token JWT en servicios REST (cabecera Authorization: Bearer).

5.3. Buenas prácticas (OWASP)

  • PreparedStatement o parámetros JPQL contra inyección SQL; codificar la salida contra XSS (JSF escapa por defecto); tokens contra CSRF (JSF los incluye en ViewState).

  • Cookies de sesión HttpOnly y Secure; renovar el identificador de sesión tras el login (changeSessionId(), Servlet 3.1).

  • Hash robusto de contraseñas (Pbkdf2PasswordHash en Jakarta Security).

  • En la Administración, integración con Cl@ve (SAML 2.0) y firma electrónica con @firma/AutoFirma, y cumplimiento del ENS (RD 311/2022).

6. Plataforma .NET: arquitectura y lenguajes

.NET es una plataforma de código abierto y multiplataforma (Windows, Linux, macOS, móviles) cuyo núcleo es el CLR, que ejecuta código gestionado compilado a CIL. La versión LTS vigente es .NET 10 (noviembre de 2025) con C# 14.

Compilación en dos etapas: código fuente (C#) → compilador Roslyn → CIL en un ensamblado → en ejecución el JIT del CLR lo traduce a código máquina. Alternativas: ReadyToRun (precompilado parcial) y Native AOT (compilación anticipada completa, sin JIT; arranque rápido).

Equivalencias con Java: CLR ≈ JVM; CIL ≈ bytecode; ensamblado ≈ JAR; NuGet ≈ Maven; BCL ≈ API de Java SE.

6.4. Rasgos de C# para test

  • Propiedades (get/set, autopropiedades, init), indexadores, eventos y delegados (punteros a función con tipo seguro; Action, Func).

  • LINQ (Language Integrated Query): consultas integradas sobre colecciones, XML o BD: from e in expedientes where e.Abierto select e.

  • async / await y Task para programación asíncrona.

  • Genéricos reificados (se conservan en ejecución, a diferencia del borrado de tipos de Java).

  • struct (valor) frente a class (referencia); record (C# 9); tipos que aceptan nulos int? y referencias anulables (C# 8).

  • Métodos no virtuales por defecto (virtual/override), sealed, abstract, interface, namespace, using.

  • Modificadores: public, private, protected, internal (ensamblado), protected internal, private protected.

  • Atributos ([Authorize], [HttpGet]) ≈ anotaciones de Java.

  • Gestión de recursos: IDisposable + using.

7. Componentes de .NET: web, persistencia y seguridad

En .NET actual la pieza central para aplicaciones empresariales es ASP.NET Core, con Entity Framework Core para persistencia y ASP.NET Core Identity / OpenID Connect para seguridad, todo unido por un contenedor de inyección de dependencias integrado.

7.1. ASP.NET Core

  • Servidor web: Kestrel (integrado, multiplataforma), opcionalmente tras un proxy inverso (IIS, Nginx). IIS era el servidor clásico de ASP.NET en .NET Framework.

  • Canalización de middleware (pipeline): cada petición atraviesa componentes en orden (UseRouting, UseAuthentication, UseAuthorization…). Equivale a los filtros de servlets.

  • Configuración en Program.cs y appsettings.json (antes Web.config y Startup.cs).

  • Inyección de dependencias integrada con tres vidas: AddTransient (nueva instancia en cada petición del servicio), AddScoped (una por petición HTTP) y AddSingleton (una para toda la aplicación).

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddDbContext<AppDb>(o => o.UseSqlServer(cadena));
builder.Services.AddScoped<IServicioExpedientes, ServicioExpedientes>();
var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.MapGet("/expedientes/{id}", (int id, AppDb db) => db.Expedientes.Find(id));
app.Run();

Tecnologías de .NET Framework que no pasaron a .NET Core/.NET moderno: ASP.NET Web Forms, WCF en servidor (alternativas: gRPC o el proyecto comunitario CoreWCF), .NET Remoting y AppDomains múltiples.

  • Enfoques de EF: Code First (las clases generan el esquema mediante migraciones) y Database First (scaffolding desde una BD existente). El Model First con diseñador visual era de EF 6 (.NET Framework).

  • Carga de relaciones: ansiosa (Include()), explícita (Load()) y perezosa (lazy loading con proxies, opcional).

  • Consultas parametrizadas por defecto en LINQ y FromSql interpolado → protección frente a inyección SQL.

7.3. Seguridad en .NET

  • Autenticación por esquemas: cookies, JWT Bearer, OpenID Connect, certificados de cliente, Windows/Negotiate (Kerberos, NTLM) en intranets con Active Directory.

  • ASP.NET Core Identity: gestión de usuarios, contraseñas (con hash PBKDF2), roles, claims, doble factor (2FA) y bloqueo de cuentas.

  • Autorización: atributo [Authorize] (con Roles = "Admin" o Policy = "..."), [AllowAnonymous]; autorización basada en roles, en claims y en políticas.

  • Protección de datos (Data Protection API), antifalsificación (antiforgery tokens contra CSRF), codificación automática en Razor contra XSS, HTTPS obligatorio con UseHttpsRedirection y HSTS.

  • Gestión de secretos: Secret Manager en desarrollo y almacenes externos (Azure Key Vault) en producción.

  • La antigua CAS (Code Access Security) de .NET Framework no existe en .NET moderno.

  • Gestión de eventos: en Java, modelo de delegación de eventos con listeners (ActionListener, addActionListener); en .NET, eventos y delegados (button.Click += Manejador).

  • Gestores de diseño (layout managers) en Swing: BorderLayout, FlowLayout, GridLayout, GridBagLayout, BoxLayout. En XAML: Grid, StackPanel, DockPanel.

  • Accesibilidad de las interfaces: obligatoria en el sector público por el RD 1112/2018 (norma UNE-EN 301 549, que remite a WCAG 2.1 nivel AA); se trata en el tema de accesibilidad del Bloque III.

Esquema de repaso

  • Jakarta EE = especificaciones (Eclipse Foundation) con varias implementaciones; .NET = plataforma de Microsoft y .NET Foundation.

  • Versiones a nov. 2026: Jakarta EE 11 (junio 2025, Java 17+); EE 12 en desarrollo (Java 21+). Java 25 LTS. .NET 10 LTS (C# 14), .NET 11 STS; en .NET, pares = LTS (3 años), impares = STS.

  • Jakarta EE 9 (dic. 2020): javax.* → jakarta.*; los paquetes de Java SE (javax.sql, javax.swing) no cambian.

  • Perfiles: Core (EE 10, microservicios), Web (EE 6), Platform (completo).

  • Contenedores: web (servlets, JSP, JSF) y EJB; servicios: ciclo de vida, DI, transacciones, seguridad, JNDI.

  • Empaquetado: JAR, WAR (web.xml), EAR (application.xml), RAR.

  • Servlet: init() → service() → destroy(); una instancia, varios hilos.

  • JSP se traduce a servlet; JSF = MVC por componentes con FacesServlet y 6 fases.

  • CDI: @Inject, @Named, ámbitos @RequestScoped, @SessionScoped, @ApplicationScoped; @Dependent por defecto.

  • EJB: @Stateless, @Stateful, @Singleton, @MessageDriven; los entity beans los sustituyó JPA.

  • JPA: @Entity, @Id, EntityManager, persistence.xml, JPQL sobre entidades; Hibernate, EclipseLink. JDBC: PreparedStatement contra inyección SQL.

  • JTA: REQUIRED por defecto, REQUIRES_NEW, MANDATORY, NEVER; 2PC para transacciones distribuidas.

  • JMS: cola (punto a punto, un consumidor) y tema (publicación/suscripción, todos los suscriptores).

  • Tomcat y Jetty son solo contenedores web; GlassFish, WildFly, WebLogic, Open Liberty, Payara son servidores completos.

  • Seguridad Java: @RolesAllowed, @PermitAll, @DenyAll; login BASIC, DIGEST, FORM, CLIENT-CERT; CONFIDENTIAL = HTTPS.

  • .NET: código C# → CIL → JIT del CLR; CTS (tipos), CLS (interoperabilidad), BCL, ensamblados .dll.

  • ASP.NET Core: MVC, Razor Pages, Web API, Minimal APIs, Blazor; servidor Kestrel; DI con AddTransient, AddScoped, AddSingleton.

  • Persistencia .NET: ADO.NET (DataReader conectado, DataSet desconectado) y EF Core (DbContext, DbSet, LINQ, migraciones).

  • Seguridad .NET: [Authorize], Identity, JWT, OpenID Connect; roles, claims y políticas.

  • Interfaces: Java → AWT, Swing, JavaFX, JSF; .NET → WinForms, WPF (XAML, MVVM), MAUI, Razor/Blazor.
