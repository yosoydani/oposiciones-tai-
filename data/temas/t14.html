Enunciado (Bloque II, tema 14): Sistemas de gestión de bases de datos relacionales, orientados a objetos y NoSQL: características y componentes.

Enunciado revisado con el Anexo V de la convocatoria (BOE-A-2025-26262). En el Anexo V figura como tema 5 del Bloque II «Tecnología básica»; es el 14 en la numeración continua del temario (Bloque I = 9 temas).

1. Conceptos básicos

Una base de datos (BD) es un conjunto de datos interrelacionados, almacenados con redundancia controlada y compartidos por varios usuarios y aplicaciones. Un sistema de gestión de bases de datos (SGBD; en inglés DBMS) es el software que permite definir, crear, consultar, mantener y controlar el acceso a la BD.

1.1. Problemas de los sistemas de ficheros que resuelve el SGBD

Redundancia e inconsistencia de datos, dificultad de acceso, aislamiento de datos, problemas de integridad, de atomicidad, de acceso concurrente y de seguridad.

1.2. Funciones de un SGBD (Codd y otros)

  • Definición de datos (esquemas) mediante un DDL.

  • Manipulación (consulta, inserción, modificación, borrado) mediante un DML.

  • Diccionario de datos (catálogo): metadatos sobre la propia BD («datos sobre los datos»).

  • Integridad: cumplimiento de restricciones.

  • Seguridad y control de acceso: usuarios, roles y privilegios.

  • Control de concurrencia y gestión de transacciones.

  • Recuperación ante fallos (copias de seguridad, registro de transacciones).

  • Optimización de consultas y gestión del almacenamiento.

1.3. Arquitectura ANSI/SPARC (1975)

Propuesta por el comité ANSI/X3/SPARC. Define tres niveles de esquema:

NivelQué describeQuién lo ve
Externo (vistas, subesquemas)La parte de la BD que interesa a cada usuario o aplicación; puede haber muchosUsuarios finales, programadores
Conceptual (lógico)Toda la BD: entidades, atributos, relaciones, restricciones; hay unoAdministrador de la BD (DBA)
Interno (físico)Cómo se almacenan los datos: ficheros, índices, rutas de acceso; hay unoSGBD, DBA

Entre niveles hay correspondencias (mappings) que dan:

  • Independencia lógica: cambiar el esquema conceptual sin afectar a los esquemas externos ni a las aplicaciones. Es más difícil de conseguir.

  • Independencia física: cambiar el esquema interno (índices, ficheros, dispositivos) sin afectar al conceptual.

1.5. Usuarios

  • DBA (administrador de la BD): define esquemas, concede permisos, gestiona copias, rendimiento y recuperación.

  • Diseñadores, programadores de aplicaciones y usuarios finales (ocasionales, paramétricos, sofisticados).

  • Árbol B / B+ (el más habitual; sirve para igualdad y rangos; en B+ los datos están en las hojas, enlazadas entre sí).

2.2. Lenguajes

  • Algunos manuales clasifican SELECT como DQL (consulta).

  • TRUNCATE es DDL: vacía la tabla sin registrar fila a fila y, en muchos SGBD, sin posibilidad de ROLLBACK. DELETE es DML y admite WHERE y ROLLBACK.

  • DML procedimental (navegacional: cómo obtener los datos, p. ej. CODASYL) frente a no procedimental / declarativo (qué datos, p. ej. SQL).

  • Extensiones procedimentales: PL/SQL (Oracle), T-SQL (SQL Server), PL/pgSQL (PostgreSQL), SQL PSM (estándar).

  • Acceso desde programas: ODBC, JDBC, ORM (Hibernate/JPA, Entity Framework), SQL embebido.

2.3. Arquitecturas de despliegue

  • Centralizada, cliente/servidor (2 o 3 capas), distribuida (datos en varios nodos; fragmentación horizontal = por filas, vertical = por columnas; replicación).

  • Paralela: memoria compartida, disco compartido o nada compartido (shared nothing).

  • En la nube (DBaaS): Amazon RDS/Aurora, Azure SQL Database, Google Cloud SQL / AlloyDB.

3. El modelo relacional

Propuesto por Edgar F. Codd (IBM) en 1970 en el artículo A Relational Model of Data for Large Shared Data Banks. Se basa en la teoría de conjuntos y la lógica de predicados.

3.1. Estructura y terminología

TeóricoTabla / SQLFicheros
RelaciónTablaFichero
TuplaFilaRegistro
AtributoColumnaCampo
GradoNúmero de columnas—
CardinalidadNúmero de filas—
DominioTipo / conjunto de valores válidos—

Propiedades de una relación: no hay tuplas duplicadas; el orden de filas y de columnas es irrelevante; cada valor es atómico; cada atributo tiene nombre distinto. Esquema (intensión, estable) frente a instancia (extensión, cambia con el tiempo).

3.2. Claves

  • Superclave: conjunto de atributos que identifica unívocamente cada tupla.

  • Clave candidata: superclave mínima (irreducible).

  • Clave primaria (PK): la candidata elegida. Claves alternativas: las demás candidatas (en SQL, UNIQUE).

  • Clave foránea o ajena (FK): atributos que referencian la clave primaria (o candidata) de otra relación (o de la misma).

  • Clave natural (dato real, p. ej. NIF) frente a subrogada (artificial, p. ej. autonumérica).

3.3. Restricciones de integridad

  • Integridad de entidad: ningún atributo de la clave primaria puede ser nulo.

  • Integridad referencial: el valor de una FK debe existir en la tabla referenciada o ser nulo.

  • Acciones referenciales en ON DELETE / ON UPDATE: CASCADE (propaga), SET NULL, SET DEFAULT, RESTRICT / NO ACTION (impide la operación).

  • Otras: de dominio, NOT NULL, UNIQUE, CHECK, disparadores (triggers) y aserciones.

  • NULL = valor desconocido o inaplicable; la lógica SQL es trivaluada (verdadero, falso, desconocido). NULL = NULL no es verdadero: se usa IS NULL.

Reglas de Codd (1985): 12 reglas (numeradas 0 a 12, es decir, 13) para considerar relacional un SGBD. Ejemplos: regla 1 de la información (todo se representa como valores en tablas), regla 2 de acceso garantizado (tabla + clave + columna), regla 3 de tratamiento sistemático de nulos, regla 4 de catálogo relacional en línea, independencia física (8), lógica (9), de integridad (10) y de distribución (11), y regla 12 de no subversión.

3.4. Álgebra y cálculo relacional

Álgebra relacional (procedimental). Operadores primitivos:

OperadorSímboloResultadoEn SQL

ProyecciónπColumnas elegidas (sin duplicados)Lista del SELECT (con DISTINCT)

Derivados: intersección (∩, INTERSECT), combinación (join) ⋈ (theta, equi, natural, externas), división (÷, «los que cumplen para todos»).

Cálculo relacional (no procedimental): de tuplas (base de QUEL/SQL) y de dominios (base de QBE). El álgebra y el cálculo tienen la misma potencia expresiva (teorema de Codd).

3.5. Normalización

Proceso que elimina redundancias y anomalías de inserción, borrado y modificación, basándose en las dependencias funcionales (X → Y: cada valor de X determina un único valor de Y).

Forma normalCondición
1FNTodos los atributos tienen valores atómicos; sin grupos repetitivos
2FN1FN + todo atributo no clave depende de la clave completa (sin dependencias parciales). Una relación en 1FN con clave simple ya está en 2FN
3FN2FN + sin dependencias transitivas (un atributo no clave no depende de otro no clave)
FNBC (Boyce-Codd)Todo determinante es clave candidata. Más estricta que 3FN
4FNFNBC + sin dependencias multivaluadas no triviales
5FN (FNPJ)Sin dependencias de combinación (join) no implicadas por las claves

  • Regla mnemotécnica: «la clave, toda la clave y nada más que la clave» (1FN, 2FN, 3FN).

  • Desnormalización: introducir redundancia controlada para mejorar el rendimiento de lectura (habitual en almacenes de datos: esquemas en estrella y copo de nieve).

  • Diseño: conceptual (E/R) → lógico (paso a tablas y normalización) → físico (índices, particiones). En el paso a tablas, una relación N:M genera una tabla intermedia con las claves de ambas entidades.

4. Transacciones, concurrencia y recuperación

Una transacción es una unidad lógica de trabajo: un conjunto de operaciones que se ejecutan todas o ninguna. Termina con COMMIT (confirmar) o ROLLBACK (deshacer).

4.1. Propiedades ACID

PropiedadSignificadoQuién la garantiza
AtomicidadTodo o nadaGestor de recuperación (registro undo)
ConsistenciaLleva la BD de un estado válido a otro válido (cumple restricciones)Programador + restricciones del SGBD
Aislamiento (Isolation)Las transacciones concurrentes no interfieren; el resultado equivale a una ejecución en serieGestor de concurrencia
DurabilidadLo confirmado persiste aunque haya fallosGestor de recuperación (registro redo, WAL)

Estados de una transacción: activa → parcialmente confirmada → confirmada; o activa → fallida → abortada (se deshace).

4.2. Anomalías de concurrencia

  • Actualización perdida: dos transacciones modifican el mismo dato y una sobrescribe a la otra.

  • Lectura sucia (dirty read): se lee un dato modificado por otra transacción no confirmada.

  • Lectura no repetible: al releer una fila, su valor ha cambiado (otra transacción la modificó y confirmó).

  • Lectura fantasma (phantom): al repetir una consulta aparecen o desaparecen filas (otra transacción insertó o borró).

Niveles de aislamiento (SQL estándar):

NivelLectura suciaNo repetibleFantasma
READ UNCOMMITTEDPosiblePosiblePosible
READ COMMITTEDEvitadaPosiblePosible
REPEATABLE READEvitadaEvitadaPosible
SERIALIZABLEEvitadaEvitadaEvitada

Nivel por defecto: READ COMMITTED en Oracle, PostgreSQL y SQL Server; REPEATABLE READ en MySQL (InnoDB).

4.3. Control de concurrencia

  • Planificación serializable: ejecución concurrente equivalente a alguna ejecución en serie (criterio de corrección).

  • Bloqueos: compartido (S, lectura), compatible con otros S; exclusivo (X, escritura), incompatible con todos. Granularidad: BD, tabla, página, fila. Escalada de bloqueos.

  • Bloqueo en dos fases (2PL): fase de crecimiento (solo adquiere) y fase de decrecimiento (solo libera). Garantiza serializabilidad, pero no evita interbloqueos. 2PL estricto: los bloqueos exclusivos se liberan al confirmar (evita cascadas de anulación).

  • Marcas de tiempo (timestamps): orden por la hora de inicio; sin bloqueos ni interbloqueos.

  • Optimista: se valida al final (fases de lectura, validación y escritura).

  • MVCC (Multiversion Concurrency Control): cada transacción ve una instantánea; los lectores no bloquean a los escritores. Lo usan PostgreSQL, Oracle, MySQL InnoDB y SQL Server (opcional).

  • Interbloqueos: el SGBD los detecta con un grafo de espera y aborta una víctima, o los previene (wait-die, wound-wait) o usa tiempos de espera.

4.4. Recuperación

  • Tipos de fallo: de transacción, del sistema (se pierde la memoria), del soporte (se pierde el disco).

  • Registro de transacciones (log / diario / redo log): anota cada cambio con valor anterior y posterior.

  • WAL (Write-Ahead Logging): el registro se escribe en disco antes que los datos modificados.

  • UNDO (deshacer transacciones no confirmadas) y REDO (rehacer las confirmadas). Algoritmo ARIES (IBM).

  • Puntos de control (checkpoints): acotan cuánto registro hay que procesar al recuperar.

  • Copias de seguridad: completa; incremental (cambios desde la última copia de cualquier tipo); diferencial (cambios desde la última completa). Copias en caliente y recuperación a un instante (PITR) con la copia + registros archivados.

  • Transacciones distribuidas: protocolo de confirmación en dos fases (2PC): 1) preparación (el coordinador pregunta y cada participante vota), 2) confirmación o anulación global. Estándar XA (X/Open).

5.3. Recordatorio de SQL

SELECT d.nombre, COUNT(*) AS empleados, AVG(e.salario) AS media
FROM empleado e
  INNER JOIN departamento d ON e.id_dep = d.id
WHERE e.alta >= DATE '2020-01-01'
GROUP BY d.nombre
HAVING COUNT(*) > 5
ORDER BY media DESC;

  • Orden lógico de evaluación: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Por eso WHERE no admite funciones de agregado y HAVING sí.

  • Agregados: COUNT, SUM, AVG, MIN, MAX. COUNT(*) cuenta filas; COUNT(columna) ignora nulos.

  • Combinaciones: INNER JOIN, LEFT/RIGHT [OUTER] JOIN (conserva las filas sin pareja de un lado), FULL OUTER JOIN, CROSS JOIN (producto cartesiano), NATURAL JOIN.

  • Subconsultas: IN, EXISTS, ANY/SOME, ALL; correlacionadas.

  • Vistas (CREATE VIEW): tablas virtuales; implementan el nivel externo de ANSI/SPARC. Vistas materializadas: almacenan el resultado.

  • Procedimientos almacenados, funciones y disparadores (BEFORE/AFTER/INSTEAD OF; a nivel de fila o de sentencia).

  • Cursores: recorren fila a fila un resultado desde código procedimental.

6. Bases de datos orientadas a objetos y objeto-relacionales

Un SGBD orientado a objetos (SGBDOO, OODBMS) almacena objetos con su estado y comportamiento, tal como los maneja un lenguaje orientado a objetos. Surgen para eliminar el desajuste de impedancia (impedance mismatch) entre el modelo de objetos de los programas y el modelo de tablas.

6.1. Conceptos clave

  • Identidad de objeto (OID): identificador único, inmutable y generado por el sistema, independiente del valor de los atributos (a diferencia de la clave primaria relacional).

  • Objetos complejos: atributos que son otros objetos o colecciones (set, bag, list, array).

  • Encapsulamiento: estado accesible solo a través de métodos.

  • Clases y herencia (simple o múltiple); polimorfismo, sobrecarga y ligadura tardía.

  • Persistencia: los objetos sobreviven al programa. Modelos: por alcanzabilidad (persiste todo lo accesible desde una raíz persistente), por herencia de una clase persistente o por declaración explícita.

  • Relaciones mediante referencias (punteros a OID) en vez de claves foráneas; navegación directa sin joins.

6.2. Manifiesto de las BDOO (Atkinson y otros, 1989)

Fija 13 características obligatorias: 8 de orientación a objetos (objetos complejos, identidad, encapsulamiento, tipos o clases, herencia, sobrecarga y ligadura tardía, completitud computacional, extensibilidad) y 5 de SGBD (persistencia, gestión del almacenamiento secundario, concurrencia, recuperación y consultas ad hoc).

6.3. Estándar ODMG

El ODMG (Object Data Management Group) publicó el estándar de BDOO (última versión ODMG 3.0, 2000). Componentes:

ComponenteFunción
Modelo de objetosBasado en el de OMG
ODL (Object Definition Language)Definir el esquema (equivale al DDL)
OQL (Object Query Language)Consultas declarativas, sintaxis parecida a SQL
BindingsEnlaces con C++, Java y Smalltalk

6.4. Productos y uso

  • Ejemplos: ObjectStore, Versant, GemStone/S, ObjectDB (Java, JPA), db4o (descontinuado), InterSystems (multimodelo).

  • Ventajas: modelado natural de datos complejos (CAD/CAM, ingeniería, multimedia, telecomunicaciones), navegación rápida, sin desajuste de impedancia, reutilización.

  • Inconvenientes: falta de un estándar consolidado y de base teórica común, menos herramientas, consultas ad hoc más limitadas, dependencia del lenguaje. Por eso su cuota de mercado es reducida.

  • En la práctica, el desajuste se resuelve casi siempre con ORM (Hibernate/JPA, Entity Framework) sobre una BD relacional.

6.5. SGBD objeto-relacionales (SGBDOR)

Extienden el modelo relacional con capacidades de objetos, manteniendo SQL. Se apoyan en el Manifiesto de tercera generación (Stonebraker y otros, 1990) y se normalizan en SQL:1999.

  • Tipos definidos por el usuario (UDT), tipos estructurados con métodos.

  • Herencia de tipos y de tablas (en PostgreSQL, INHERITS).

  • Referencias (REF) a filas-objeto, colecciones (arrays, tablas anidadas).

  • Objetos grandes (BLOB, CLOB), funciones y operadores de usuario.

  • Ejemplos: PostgreSQL (se define como «objeto-relacional»), Oracle (tipos de objeto, VARRAY, nested tables), IBM Db2, Informix.

7. Bases de datos NoSQL

NoSQL («Not only SQL») agrupa SGBD no relacionales pensados para grandes volúmenes, escalado horizontal en clústeres de máquinas baratas, alta disponibilidad y esquemas flexibles (schema-less o esquema en lectura). El término se popularizó en 2009. Precedentes: los artículos de Google Bigtable (2006) y Amazon Dynamo (2007).

7.1. Características comunes

  • Sin esquema fijo: cada registro puede tener campos distintos.

  • Escalado horizontal (scale-out) añadiendo nodos, frente al vertical (scale-up) típico del relacional.

  • Particionado (sharding): reparto de los datos entre nodos por clave; a menudo con hash consistente.

  • Replicación: maestro-esclavo (primario-secundarios) o entre iguales (peer-to-peer, sin maestro).

  • Modelo orientado a agregados: se guarda junto lo que se lee junto; se desnormaliza y se evitan los joins.

  • Consistencia normalmente eventual y a menudo ajustable (quórum: con N réplicas, si R + W > N las lecturas ven la última escritura).

  • APIs propias o lenguajes específicos; procesamiento masivo con MapReduce.

7.2. Teorema CAP (Brewer)

Formulado por Eric Brewer en 2000 y demostrado por Gilbert y Lynch en 2002. Un sistema distribuido no puede garantizar a la vez las tres propiedades:

PropiedadSignificado
Consistencia (Consistency)Todos los nodos ven el mismo dato al mismo tiempo (la última escritura)
Disponibilidad (Availability)Toda petición a un nodo activo recibe respuesta
Tolerancia a Particiones (Partition tolerance)El sistema sigue funcionando aunque se corte la comunicación entre nodos

Como en un sistema distribuido las particiones de red son inevitables, ante una partición hay que elegir entre C y A:

  • CP (prioriza consistencia): HBase, MongoDB (configuración por defecto con un primario), Redis Cluster, etcd, ZooKeeper.

  • AP (prioriza disponibilidad): Cassandra, CouchDB, Riak, DynamoDB (lecturas eventuales por defecto).

  • CA: solo tiene sentido sin particiones: SGBD relacional en un único nodo.

  • PACELC (Abadi): si hay Partición, elegir A o C; En otro caso (Else), elegir Latencia o Consistencia.

7.3. BASE frente a ACID

ACID (relacional)BASE (NoSQL)
Atomicidad, Consistencia, Aislamiento, DurabilidadBasically Available (básicamente disponible), Soft state (estado flexible), Eventual consistency (consistencia eventual)
Consistencia fuerteConsistencia eventual: si no hay nuevas escrituras, todas las réplicas acaban convergiendo
Pesimista, prioriza la correcciónOptimista, prioriza la disponibilidad

Muchos NoSQL actuales ya ofrecen transacciones ACID (p. ej. MongoDB desde la versión 4.0 para múltiples documentos).

  • Lenguajes de grafos: Cypher (Neo4j), Gremlin (Apache TinkerPop), SPARQL (grafos RDF, W3C) y GQL (norma ISO/IEC 39075, 2024).

  • Grafos de propiedades (nodos y aristas con atributos) frente a RDF (tripletas sujeto-predicado-objeto).

  • No confundir columnares de familias de columnas (Cassandra, HBase) con SGBD relacionales columnares analíticos (almacenan por columnas para OLAP: ClickHouse, Amazon Redshift, Vertica).

Otros tipos frecuentes: series temporales (InfluxDB, TimescaleDB), motores de búsqueda (Elasticsearch, OpenSearch, basados en Apache Lucene), vectoriales para IA (Milvus, Pinecone, extensión pgvector de PostgreSQL), multimodelo (ArangoDB, Azure Cosmos DB) y BD en memoria.

Tendencias:

  • Persistencia políglota: cada aplicación usa el almacén más adecuado para cada tipo de dato.

  • Convergencia: los relacionales añaden JSON, grafos (SQL/PGQ en SQL:2023) y vectores; los NoSQL añaden SQL y transacciones.

  • NewSQL: relacionales distribuidos con ACID y escalado horizontal: Google Spanner, CockroachDB, TiDB, YugabyteDB.

  • Bases de datos en la nube y sin servidor (serverless), BD autogestionadas y gestionadas (DBaaS).

  • IA: búsqueda vectorial integrada (Oracle 26ai, SQL Server 2025, pgvector) para aplicaciones de IA generativa (RAG).

  • Analítica: almacenes de datos (OLAP), data lakes y lakehouse; formatos abiertos (Parquet, Apache Iceberg).

  • En la Administración española, el Esquema Nacional de Interoperabilidad (ENI) y el Esquema Nacional de Seguridad (ENS) condicionan formatos, conservación y medidas de seguridad de los datos.

Esquema de repaso

  • BD = datos interrelacionados con redundancia controlada; SGBD = software que los define, manipula y controla.

  • ANSI/SPARC (1975): niveles externo (muchos), conceptual (uno) e interno (uno).

  • Independencia lógica (conceptual sin tocar externos; más difícil) y física (interno sin tocar conceptual).

  • Modelos: jerárquico (IMS), en red (CODASYL), relacional (Codd, 1970), OO, objeto-relacional, NoSQL, NewSQL; E/R de Chen (1976).

  • Componentes: procesador y optimizador de consultas, gestores de transacciones, concurrencia, recuperación, búfer y almacenamiento; diccionario de datos.

  • DDL (CREATE, ALTER, DROP, TRUNCATE), DML (SELECT, INSERT, UPDATE, DELETE), DCL (GRANT, REVOKE), TCL (COMMIT, ROLLBACK, SAVEPOINT).

  • Relación = tabla; grado = columnas; cardinalidad = filas; sin duplicados, sin orden, valores atómicos.

  • Claves: superclave → candidata (mínima) → primaria / alternativas; foránea.

  • Integridad de entidad (PK no nula) y referencial (CASCADE, SET NULL, RESTRICT…).

  • Álgebra: primitivos σ, π, ∪, −, × (+ ρ); derivados ∩, ⋈, ÷.

  • Normalización: 1FN atómicos, 2FN sin dependencias parciales, 3FN sin transitivas, FNBC todo determinante es clave candidata, 4FN multivaluadas.

  • ACID: atomicidad, consistencia, aislamiento, durabilidad.

  • Anomalías: lectura sucia, no repetible, fantasma; niveles READ UNCOMMITTED → SERIALIZABLE (evita todas).

  • 2PL garantiza serializabilidad (no evita interbloqueos); MVCC; WAL; UNDO/REDO; 2PC en distribuidas.

  • Copias: completa, incremental (desde la última de cualquier tipo), diferencial (desde la última completa).

  • Versiones: Oracle AI Database 26ai, SQL Server 2025, PostgreSQL 18, MySQL 8.4 / 9.7 LTS y 26.10 Innovation. SQL = ISO/IEC 9075; SQL:1999 objeto-relacional; SQL:2023 JSON y grafos.

  • BDOO: OID, encapsulamiento, herencia, persistencia por alcanzabilidad; manifiesto de 1989 (13 reglas); ODMG 3.0: ODL, OQL.

  • Objeto-relacional: UDT, herencia, REF, colecciones (PostgreSQL, Oracle).

  • CAP (Brewer 2000; Gilbert y Lynch 2002): ante partición, C o A. CP: HBase, MongoDB. AP: Cassandra, CouchDB. BASE: básicamente disponible, estado flexible, consistencia eventual.

  • NoSQL: clave-valor (Redis, DynamoDB), documentales (MongoDB, CouchDB), familias de columnas (Cassandra, HBase, Bigtable), grafos (Neo4j/Cypher, Neptune).
